The DNS front answers the zone apex of dnstt zones, and dnstt answers a resolver's retry with the first answer's data. For raycontrol v0.12.

- DNS front: dns.zones[].ns. With the names a zone is delegated to, the front answers at the zone's apex itself: SOA and NS as records, any other type NOERROR with no record and the SOA in authority (RFC 2308). Some resolvers gave SERVFAIL for a delegated zone whose apex had neither. The answers are built as dnstt's (QR and AA, the question as asked, OPT 4096 when the query had one), so the names go to dnstt zones only. An answer larger than the requester's size (512 without OPT) goes out with TC and no records. A query not of class IN, not a QUERY or with an EDNS version other than 0 goes to the backend as before.
- dnstt: a query asked again (a resolver's retry: the same payload, its name in any case or split into labels otherwise) gets the data of the first answer for 5 to 10 seconds, at most 8192 answers kept. A resolver passes on whichever answer comes first and drops the other; new data in the retry's answer was lost, and KCP had to send it again. A copy of a client's query sent by someone else gets the same bytes, not the client's next data; the client's own queries never repeat (random padding). Data that would not fit a retry's requester size goes out as an empty answer. Measured on loopback through a resolver that retries after 50 or 150 ms, with the inner stage answering 200 ms late: 20 echoes of 1 KB, the worst 530 ms before, 514 ms after; bulk transfer unchanged.
- Tests: the apex answers, also parsed by dnspython, and TC for names too long for the requester; the memo in sendLoop (retry in another case, smaller requester, another query, the clock); a retrying resolver for measurements (NIKO_MEMO_BENCH=1); the SOA through the real front beside a dnstt backend with dnsauth required.

DNS-фронт отвечает на вершине зон dnstt, а dnstt на повтор резолвера отдаёт данные первого ответа. Для raycontrol v0.12.

- DNS-фронт: dns.zones[].ns. С именами, на которые делегирована зона, фронт сам отвечает на её вершине: SOA и NS — записями, на любой другой тип — NOERROR без записей и с SOA в authority (RFC 2308). Часть резолверов без SOA и NS у вершины делегированной зоны давала SERVFAIL. Ответы собраны как ответы dnstt (QR и AA, вопрос как пришёл, OPT 4096, если он был в запросе), поэтому имена ставятся только зонам dnstt. Ответ больше размера запрашивающего (512 без OPT) уходит с TC и без записей. Запрос не класса IN, не QUERY или с версией EDNS не 0 идёт в бэкенд, как раньше.
- dnstt: повторённый запрос (повтор резолвера: те же данные запроса, имя в любом регистре или иначе разбитое на метки) получает данные первого ответа в течение 5–10 секунд, хранится не больше 8192 ответов. Резолвер отдаёт клиенту тот ответ, что пришёл первым, а второй выбрасывает; новые данные в ответе на повтор терялись, и KCP отправлял их заново. Копия чужого запроса получает те же байты, а не следующие данные клиента; свои запросы клиент не повторяет (случайная набивка). Данные, которые не помещаются в размер запрашивающего повтор, не отправляются: ответ уходит пустым. Замер на loopback через резолвер, повторяющий запрос через 50 или 150 мс, при ответе внутренней стадии с задержкой 200 мс: 20 эхо по 1 КБ, худшее — 530 мс до, 514 мс после; сплошная передача без изменений.
- Тесты: ответы вершины, в том числе разобранные dnspython, и TC для имён, не влезающих в размер запрашивающего; повтор ответов в sendLoop (повтор в другом регистре, меньший запрашивающий, другой запрос, часы); резолвер с повторами для замеров (NIKO_MEMO_BENCH=1); SOA через настоящий фронт рядом с бэкендом dnstt с dnsauth required.
