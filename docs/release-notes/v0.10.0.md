dnstt with its framing sealed (dnsseal-v1). For raycontrol v0.13.

- dnstt: options seal (off, optional, required) and seal_key_file (raycontrol docs/spec/dnsseal-v1.md). The framing a DPI that knows dnstt reads — the ClientID in every query, the padding byte, packet lengths, KCP headers in answers — is sealed with the zone's key: ChaCha20 under keys derived from it, a random nonce in each query and each answer, four zero bytes under the seal as a check of the key. Answers are padded to a multiple of 64 bytes within the requester's size. Under the seal is what dnstt sends without it, the dnsauth-v1 tag included. optional takes open queries too and answers each in its own format; required answers an open query NODATA. Up to four keys, the current first: the others are accepted while clients move to a new one; the key file is read again when it changes, without a restart. Sessions in a zone with a seal have an MTU 8 bytes smaller.
- DNS front: zones[].seal_pad pads the probe's answers (dnsprobe-v1) in a zone whose answers are sealed, as they are padded.
- dnstt: the retry memo (v0.9.0) keys by the query as it came, the seal's N with it: two sealed polls of a session with the same inner payload are two queries, not a retry. The stash takes a sealed answer's R into account when it swaps a packet.
- Fuzz targets for what the front and dnstt read off the internet: DNS queries (name, zone, apex, probe; dnstt with every mode of auth and seal), the IPC header, ClientHello, QUIC Initial, the seal and dnsauth. The IPC header now refuses an IPv4-mapped address under family 6, which the front never writes.
- Tests: vectors worked out apart from this code (Python, ChaCha20 of cryptography); a stock dnstt client through a resolver that seals by the spec alone (its own code, not dnsttserver's), in required and optional modes; an open query in a required zone gets NODATA; probe answers padded.

dnstt с запечатанной обвязкой (dnsseal-v1). Для raycontrol v0.13.

- dnstt: параметры seal (off, optional, required) и seal_key_file (raycontrol docs/spec/dnsseal-v1.md). Обвязка, по которой DPI узнаёт dnstt, — ClientID в каждом запросе, байт набивки, длины пакетов, заголовки KCP в ответах — запечатана ключом зоны: ChaCha20 под выведенными из него ключами, случайный nonce в каждом запросе и каждом ответе, четыре нулевых байта под печатью как проверка ключа. Ответы добиваются до кратного 64 байтам в пределах размера запрашивающего. Под печатью то же, что dnstt шлёт без неё, метка dnsauth-v1 тоже. optional берёт и открытые запросы и отвечает каждому в его формате; required отвечает на открытый запрос NODATA. До четырёх ключей, первым текущий: остальные принимаются, пока клиенты переходят на новый; файл ключей перечитывается при изменении, без перезапуска. MTU сессий в зоне с печатью на 8 байт меньше.
- DNS-фронт: zones[].seal_pad добивает ответы на пробу (dnsprobe-v1) в зоне с запечатанными ответами так же, как добиваются они.
- dnstt: память ответов на повторы (v0.9.0) ищет по запросу как он пришёл, вместе с N печати: два запечатанных опроса сессии с одинаковым содержимым — два запроса, а не повтор. Подмена пакета в отложенных учитывает R запечатанного ответа.
- Цели фаззинга для того, что фронт и dnstt читают из сети: DNS-запросы (имя, зона, apex, проба; dnstt во всех режимах auth и seal), заголовок IPC, ClientHello, QUIC Initial, печать и dnsauth. Заголовок IPC больше не берёт IPv4-mapped адрес с семейством 6: фронт так не пишет.
- Тесты: векторы, посчитанные отдельно от кода (Python, ChaCha20 из cryptography); обычный клиент dnstt через резолвер, который запечатывает по одной спеке (свой код, не dnsttserver), в режимах required и optional; открытый запрос в зоне required получает NODATA; добивка ответов пробы.
