dnstt with its framing sealed (dnsseal-v1). For raycontrol v0.13.

- dnstt: options seal (off, optional, required) and seal_key_file (raycontrol docs/spec/dnsseal-v1.md). The framing a DPI that knows dnstt reads — the ClientID in every query, the padding byte, packet lengths, KCP headers in answers — is sealed with the zone's key: ChaCha20 under keys derived from it, a random nonce in each query and each answer, and a tag of 4 bytes (HMAC-SHA256 under its own key, over the nonce and the ciphertext) that tells the key and lets nothing under the seal be changed on the way. Answers are padded to a multiple of 64 bytes within the requester's size. Under the seal is what dnstt sends without it, the dnsauth-v1 tag included. optional takes open queries too and answers each in its own format; required answers an open query NODATA. Up to four keys, the current first: the others are accepted while clients move to a new one; the key file is read again when it changes, without a restart. Sessions in a zone with a seal have an MTU 12 bytes smaller.
- DNS front: zones[].seal_pad pads the probe's answers (dnsprobe-v1) in a zone whose answers are sealed, as they are padded.
- dnstt: the retry memo (v0.9.0) keys by the query as it came, the seal's N with it: two sealed polls of a session with the same inner payload are two queries, not a retry. The stash takes a sealed answer's R into account when it swaps a packet.
- DNS front: a backend's answer goes out only to a query that waits for it (the same client and ID, within 5 to 10 seconds), never larger than its requester takes (the OPT's size wherever it is, 512 without one) and never over 1232 bytes whatever the OPT says; a larger one goes as TC with no records. masterdns sent its MTU probes' kilobytes whatever the requester's size, so a forged source made the node a reflector (a query of ~100 bytes, 4 to 6 KB to the victim, 136 times with a forged OPT); now a forged query gets no more than any EDNS answer.
- dnstt under load (a load test with everything on, on one vCPU): a flood of fresh ClientIDs opened KCP sessions without end wherever queries need no device tag (auth off or optional, or the seal alone) — 2.4 GB in a minute, the backend killed in a 512 MiB cgroup. Now a new ClientID reaches KCP only with a packet that starts a session (a PUSH segment with sn 0 carrying the length of the Noise first message), and at most 512 sessions, 128 of them before the end of the Noise handshake, 32 new a second; a handshake in 20 s with a first message of 512 bytes at most; a ClientID without a session gets an empty answer and no queues; queues live a minute after the last query; smux holds 256 KiB a session, 128 KiB a stream. The same floods stay under 40 MiB. The dnstt dns package (vendored, third_party/dnstt) no longer builds a message to check each name: half the CPU per query. Lines a query can cause are rate-limited; the front drops DNS datagrams over 4096 bytes; the probe checks its rate before it parses. Legit: 17.7 MB/s down on one vCPU for 50 sealed, tagged sessions.
- Fuzz targets for what the front and dnstt read off the internet: DNS queries (name, zone, apex, probe; dnstt with every mode of auth and seal), the IPC header, ClientHello, QUIC Initial, the seal and dnsauth. The IPC header now refuses an IPv4-mapped address under family 6, which the front never writes.
- Tests: vectors worked out apart from this code (Python, ChaCha20 of cryptography); a stock dnstt client through a resolver that seals by the spec alone (its own code, not dnsttserver's), in required and optional modes; an open query in a required zone gets NODATA; probe answers padded.

dnstt с запечатанной обвязкой (dnsseal-v1). Для raycontrol v0.13.

- dnstt: параметры seal (off, optional, required) и seal_key_file (raycontrol docs/spec/dnsseal-v1.md). Обвязка, по которой DPI узнаёт dnstt, — ClientID в каждом запросе, байт набивки, длины пакетов, заголовки KCP в ответах — запечатана ключом зоны: ChaCha20 под выведенными из него ключами, случайный nonce в каждом запросе и каждом ответе и метка из 4 байт (HMAC-SHA256 своим ключом от nonce и шифротекста): по ней видно ключ, и под печатью ничего не изменить по пути. Ответы добиваются до кратного 64 байтам в пределах размера запрашивающего. Под печатью то же, что dnstt шлёт без неё, метка dnsauth-v1 тоже. optional берёт и открытые запросы и отвечает каждому в его формате; required отвечает на открытый запрос NODATA. До четырёх ключей, первым текущий: остальные принимаются, пока клиенты переходят на новый; файл ключей перечитывается при изменении, без перезапуска. MTU сессий в зоне с печатью на 12 байт меньше.
- DNS-фронт: zones[].seal_pad добивает ответы на пробу (dnsprobe-v1) в зоне с запечатанными ответами так же, как добиваются они.
- dnstt: память ответов на повторы (v0.9.0) ищет по запросу как он пришёл, вместе с N печати: два запечатанных опроса сессии с одинаковым содержимым — два запроса, а не повтор. Подмена пакета в отложенных учитывает R запечатанного ответа.
- DNS-фронт: ответ бэкенда уходит только на запрос, который его ждёт (тот же клиент и ID, в пределах 5–10 секунд), не больше, чем берёт запрашивающий (размер из OPT, где бы он ни стоял; без него 512), и не больше 1232 байт, что бы ни говорил OPT; больший уходит с TC и без записей. masterdns слал килобайты ответов на пробы MTU, не глядя на размер запрашивающего, и с поддельным адресом источника нода становилась отражателем (запрос ~100 байт — 4–6 КБ жертве, со своим OPT — в 136 раз); теперь поддельный запрос получает не больше обычного ответа EDNS.
- dnstt под нагрузкой (нагрузочный тест со всем включённым, на одном vCPU): поток свежих ClientID открывал сессии KCP без конца везде, где запросу не нужна метка устройства (auth off или optional, или одна печать) — 2,4 ГБ за минуту, бэкенд убит в cgroup на 512 МиБ. Теперь новый ClientID попадает в KCP только с пакетом, который начинает сессию (сегмент PUSH с sn 0 и длиной первого сообщения Noise), и не больше 512 сессий, из них 128 до конца рукопожатия Noise, новых — 32 в секунду; рукопожатие за 20 с и с первым сообщением до 512 байт; ClientID без сессии получает пустой ответ и очередей не заводит; очереди живут минуту после последнего запроса; smux держит 256 КиБ на сессию, 128 КиБ на поток. Те же потоки — меньше 40 МиБ. Пакет dns из dnstt (своя копия, third_party/dnstt) больше не строит сообщение ради проверки каждого имени: половина CPU на запрос. Строки журнала, которые вызывает запрос, ограничены; фронт отбрасывает датаграммы DNS больше 4096 байт; проба проверяет лимит до разбора. Честный трафик: 17,7 МБ/с вниз на одном vCPU для 50 запечатанных и подписанных сессий.
- Цели фаззинга для того, что фронт и dnstt читают из сети: DNS-запросы (имя, зона, apex, проба; dnstt во всех режимах auth и seal), заголовок IPC, ClientHello, QUIC Initial, печать и dnsauth. Заголовок IPC больше не берёт IPv4-mapped адрес с семейством 6: фронт так не пишет.
- Тесты: векторы, посчитанные отдельно от кода (Python, ChaCha20 из cryptography); обычный клиент dnstt через резолвер, который запечатывает по одной спеке (свой код, не dnsttserver), в режимах required и optional; открытый запрос в зоне required получает NODATA; добивка ответов пробы.
