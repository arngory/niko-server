QUIC connections behind the UDP front outlive a change of the client's address (raycontrol docs/spec/quic-cid-route-v1.md): a NAT that gives the client another port, as mobile networks do, and a client that moves its connection to a new socket, as Niko does at a slot change of a rotating port (raycontrol spa-v2 §11). The QUIC backends give their server connection IDs a label, and the front reads it from a packet of an address it does not know yet. Off unless raycontrol writes the key and the labels; IPC is as before. Built with Go 1.27.4.

- Front: udp.cid_key_file, the node's secret (32 bytes in hex), and backends.<name>.cid_label, a QUIC backend's label (1-65535, one per backend, a backend of a UDP route only). A datagram no flow explains that is not an Initial, a short header or a Handshake of QUIC v1 or v2 with an 8-byte destination connection ID, plain or under the salamander of a route's password, is opened: the ID is Speck64/128 under a key from the secret of label (16 bits), a zero byte and a counter (40 bits). A label of a backend of that kind (a plain QUIC backend's in the clear, the salamander route's own under its salamander) pins the flow to it and the datagram goes as it came. Initials are routed by name as before; a client's first ID is its own. The flow is a flow like any other (idle time, the table's ceiling); per source (an IPv4 address, an IPv6 /64) 32 such new flows a second, burst 128. A key file that does not read is a warning: the front serves without routing by ID.
- Front: cost. A datagram no flow explains costs, on top of what it cost before, one Speck decryption if it looks like a short header or a Handshake, and one per salamander password (whose key it computed already for the Initial). No allocation on the way to a drop; a random 8 bytes read as one of k labels about k·2^-24 of the time.
- Front: a restart no longer ends the QUIC connections of labelled backends: their next packet pins a flow again. A flow forgotten after its idle time likewise.
- Hysteria2: options.cid_key_file and options.cid_label, both or neither, as the front has them. The server's connection IDs are 8 bytes with the label, and the server moves to a client's new address at its first packet from there (sing-quic's DisablePathManager, which port hopping needs). Without them, or with a key file that does not read (a warning), the IDs are quic-go's, random, 4 bytes.
- sing-quic (third_party): the Hysteria2 service and qtls.ListenWithOptions take a quic.ConnectionIDGenerator.
- What an observer sees: server connection IDs of 8 bytes (hy2-masq's were 4, rayd's naive-quic and DoH3 have had 8), each new, random to anyone without the key; the same length behind every QUIC service of the node.
- Tests: the label's code (Speck's vector from the paper, the spec's example, which raycontrol checks too), the front's routing of short headers and Handshakes from a new address, plain and under salamander, the per-source bound, no allocation on a miss; a Hysteria2 client whose NAT gives it new ports mid-connection (hy2-masq and hy2-obfs; without labels the connection is lost, as before); a quic-go HTTP/3 server on the packet socket, as rayd's, with NAT rebinding and with the client's own move (AddPath, Probe, Switch): quic-go's server validates the path through the packet socket and moves there. Fuzz targets FuzzCIDRoute and FuzzCIDCodec. A classic BPF program of 590 instructions reads the same labels (a test): the label serves naive-udp-v1 §5.2 step (г), a socket chosen by the kernel.
- For raycontrol: write udp.cid_key_file, backends.*.cid_label, options.cid_key_file and options.cid_label only to a niko-server of v0.18.0 or later: an older one refuses an unknown field, and with it the whole config.

Соединения QUIC за фронтом UDP переживают смену адреса клиента (raycontrol docs/spec/quic-cid-route-v1.md): NAT, который дал клиенту другой порт, как бывает на мобильных сетях, и клиент, который перенёс соединение на новый сокет, как Niko при смене слота ротируемого порта (raycontrol spa-v2 §11). Бэкенды QUIC дают своим connection ID метку, а фронт читает её из пакета с адреса, которого ещё не знает. Выключено, пока raycontrol не пишет ключ и метки; IPC прежний. Собрано на Go 1.27.4.

- Фронт: udp.cid_key_file — секрет ноды (32 байта в hex), и backends.<имя>.cid_label — метка бэкенда QUIC (1–65535, своя у каждого, только у бэкенда маршрута UDP). Датаграмма, которую не объясняет ни один поток и которая не Initial, — короткий заголовок или Handshake QUIC v1 или v2 с connection ID назначения в 8 байт, открытый или под salamander пароля маршрута, — вскрывается: ID — это Speck64/128 под ключом из секрета от метки (16 бит), нулевого байта и счётчика (40 бит). Метка бэкенда того же вида (открытая — обычного бэкенда QUIC, под salamander — бэкенда этого маршрута) закрепляет поток за ним, датаграмма уходит как пришла. Initial по-прежнему идёт по имени: первый ID клиента — его собственный. Поток как любой другой (простой, потолок таблицы); с источника (адрес IPv4, /64 IPv6) — 32 таких новых потока в секунду, запас 128. Ключ не читается — warning, фронт работает без маршрутизации по ID.
- Фронт: цена. Датаграмма без потока стоит сверх прежнего одного расшифрования Speck, если похожа на короткий заголовок или Handshake, и по одному на пароль salamander (ключ которого фронт и так считал для Initial). До отбрасывания — без выделений памяти; случайные 8 байт читаются как одна из k меток примерно в k·2^-24 случаев.
- Фронт: перезапуск больше не обрывает соединения QUIC бэкендов с меткой: следующий пакет снова закрепляет поток. Так же поток, забытый после простоя.
- Hysteria2: options.cid_key_file и options.cid_label, оба или ни одного, как у фронта. Connection ID сервера — 8 байт с меткой, и сервер переходит на новый адрес клиента с первого пакета оттуда (DisablePathManager sing-quic, нужный port hopping). Без них или с ключом, который не читается (warning), ID — от quic-go, случайные, 4 байта.
- sing-quic (third_party): сервис Hysteria2 и qtls.ListenWithOptions берут quic.ConnectionIDGenerator.
- Что видит наблюдатель: connection ID сервера в 8 байт (у hy2-masq было 4, у naive-quic и DoH3 в rayd давно 8), каждый новый, случайный для всех без ключа; одна длина за всеми сервисами QUIC ноды.
- Тесты: код метки (вектор Speck из статьи, пример спеки, который проверяет и raycontrol), маршрутизация фронтом коротких заголовков и Handshake с нового адреса, открытых и под salamander, предел на источник, отсутствие выделений на промахе; клиент Hysteria2, которому NAT посреди соединения даёт новые порты (hy2-masq и hy2-obfs; без меток соединение теряется, как раньше); сервер HTTP/3 quic-go на пакетном сокете, как в rayd, при NAT rebinding и при переходе самого клиента (AddPath, Probe, Switch): сервер quic-go проверяет путь через пакетный сокет и переходит на него. Fuzz-цели FuzzCIDRoute и FuzzCIDCodec. Классическая BPF-программа в 590 инструкций читает те же метки (тест): метка годится и для шага (г) naive-udp-v1 §5.2, где сокет выбирает ядро.
- Для raycontrol: udp.cid_key_file, backends.*.cid_label, options.cid_key_file и options.cid_label писать только niko-server v0.18.0 и новее: более старый отвергает незнакомое поле, а с ним и весь конфиг.
