# Конфиги niko-server (схема 1, черновик)

Черновик для согласования с raycontrol, замораживается на R1. После заморозки любое несовместимое изменение
поднимает `schema`. niko-server отказывается запускаться с незнакомой `schema` (`check` пишет почему).
JSON Schema появится в `arngory/sing-box`, `cmd/niko-server/schema/` вместе с кодом.

Общие правила:
- формат — JSON;
- секреты только путями к файлам (`*_file`): `/run/credentials/<юнит>.service/<имя>` из `LoadCredential=` (имя юнита полное, с `.service`, например `/run/credentials/niko-dns.service/noise.key`);
- длительности — строки Go (`"60s"`, `"10m"`);
- `SIGHUP` перечитывает файлы пользователей и ключей (`users_file`, `*_key_file`); остальные поля — только при перезапуске.
  У DNS-туннелей пользователей нет: их бэкенды на `SIGHUP` только пишут в лог, новый ключ — перезапуск.
- имена — по имени сервиса в raycontrol, не по виду: сервис `dns` вида `dnstt` → бэкенд `dns`,
  сокет `/run/niko/dns/packet.sock`, юнит `niko-dns.service`; вид — поле `kind`.
- UID: фронт 9100, бэкенды и Xray 9110–9179 (raycontrol R1-6).

## Проверка (`niko-server check -c FILE [--json]`)

- Коды выхода: `0` — конфиг верен, `1` — ошибка конфига, `2` — ошибка окружения (файл не читается).
- `--json` печатает массив `[{"path": "dns.zones[0].backend", "error": "…"}]`, пустой — если всё верно.
- `check` не открывает файлы секретов (`LoadCredential=` есть только внутри юнита): пути проверяются на форму,
  содержимое — при запуске (ошибка — код 2).

## Фронт

```json
{
  "schema": 1,
  "role": "front",
  "log": {"level": "warn"},
  "tcp": {
    "listen": ["0.0.0.0:443", "[::]:443"],
    "sniff_timeout": "5s",
    "acme_listen": ["0.0.0.0:9443", "[::]:9443"],
    "routes": [
      {"sni": ["k3f.example.com"], "backend": "xray-reality"},
      {"sni": ["p8w.example.com"], "backend": "naive"},
      {"sni": ["q2m.example.com"], "backend": "yggdrasil"},
      {"alpn": ["acme-tls/1"], "backend": "acme"}
    ],
    "default": "xray-reality"
  },
  "udp": {
    "listen": ["0.0.0.0:443", "[::]:443"],
    "idle": "60s",
    "routes": [
      {"sni": ["h7d.example.com"], "backend": "hy2-masq"},
      {"sni": ["p8w.example.com"], "backend": "naive-quic"},
      {"salamander_password_file": "/run/credentials/niko-front.service/salamander", "backend": "hy2-obfs"}
    ]
  },
  "dns": {
    "listen": ["0.0.0.0:53", "[::]:53"],
    "zones": [
      {"zone": "t5x.example.com", "backend": "dnstt", "probe": true, "ns": ["xk2.example.com"]},
      {"zone": "v9c.example.com", "backend": "masterdns"}
    ],
    "probe_key_file": "/run/credentials/niko-front.service/dnsprobe.key"
  },
  "backends": {
    "xray-reality": {"socket": "/run/niko/xray-reality/reality.sock", "mode": "proxy-v2", "uid": 9110},
    "naive":        {"socket": "/run/niko/naive/fd.sock",          "mode": "fd",       "uid": 9111},
    "yggdrasil":    {"socket": "/run/niko/yggdrasil/fd.sock",      "mode": "fd",       "uid": 9112},
    "acme":         {"socket": "/run/niko/acme/fd.sock",           "mode": "fd",       "uid": 9113},
    "hy2-masq":     {"socket": "/run/niko/hy2-masq/packet.sock",   "mode": "packet",   "uid": 9114},
    "hy2-obfs":     {"socket": "/run/niko/hy2-obfs/packet.sock",   "mode": "packet",   "uid": 9115},
    "naive-quic":   {"socket": "/run/niko/naive/packet.sock",      "mode": "packet",   "uid": 9111},
    "dnstt":        {"socket": "/run/niko/dnstt/packet.sock",      "mode": "packet",   "uid": 9116},
    "masterdns":    {"socket": "/run/niko/masterdns/packet.sock",  "mode": "packet",   "uid": 9117}
  }
}
```

- `mode`: `fd` — передача сокета (`SCM_RIGHTS`), `proxy-v2` — поток с заголовком PROXY v2 (Xray), `packet` — датаграммы
  с заголовком адреса. Формат и права — [`IPC.md`](IPC.md). `uid` — ожидаемый `SO_PEERCRED` бэкенда.
- `devices` (необязательно, с v0.14.0): фронт называет бэкенду устройство каждого запроса (IPC версии 2, жетон
  устройства, чью метку он проверил). Только у бэкенда в режиме `packet`, все зоны которого с `tag` и который не
  стоит в `udp.routes`, иначе ошибка `check`. Сервер slipstream (server-v0.2.0) по нему держит предел соединений
  на устройство (`--max-connections-per-device`); более старый сервер версию 2 не берёт.
- Маршрут без бэкенда в `backends` — ошибка `check`.
- Секции `tcp`, `udp`, `dns` необязательны: нет маршрутов — нет секции, фронт этот порт не слушает. Нужна хотя бы
  одна. Фронт обслуживает `dns` (с v0.1), `tcp` (с v0.2) и `udp` (с v0.3).
- `dns.listen` занимается с SO_REUSEADDR (с v0.8.2): заглушка systemd-resolved на 127.0.0.53:53 и 127.0.0.54:53
  (тоже с SO_REUSEADDR) остаётся, датаграммы на её адреса ядро отдаёт ей, остальные — фронту.
- `dns.probe_key_file` (необязательно, с v0.8.3): ключ dnsprobe-v1 (raycontrol `docs/spec/dnsprobe-v1.md`), 32 байта
  в hex. С ним фронт сам отвечает на проверку резолвера клиентом в зонах с `"probe": true`: одна метка base32 под
  зоной с MAC этого ключа, TXT. Флаг ставится только зонам dnstt: ответ пробы собран как ответ dnstt (QR и AA, TTL 60,
  OPT 4096), а у masterdns ответы другие. Данные TXT — случайный nonce ответа (8 байт) и шифротекст: токен под MAC,
  что увидела нода (размер EDNS, 0x20, адрес резолвера), у большой пробы — нули до 900 байт. Большой ответ уходит,
  только если dnstt поместил бы столько данных в ответ этому запрашивающему, иначе — малый. Частота ограничена по
  источнику (/24, /48) и в целом. Запрос без верного MAC или устаревший идёт в бэкенд зоны как обычно, dnsauth пробу
  не касается. Если файл ключа не читается, фронт пишет предупреждение и работает без проб: туннели, TCP и UDP 443
  не останавливаются. `"probe": true` без `dns.probe_key_file` — ошибка `check`. Снаружи ответ пробы — ответ dnstt по форме, но его данные не кадры KCP: тот, кто разбирает кадры
  dnstt в ответах, отличит пробу, но он и туннель уже видит.
- `dns.zones[].seal_pad` (необязательно, с v0.10.0, нужен `probe`): ответы dnstt в зоне запечатаны (dnsseal-v1,
  `required`), и фронт добивает данные TXT своих ответов на пробу так же: случайными байтами до кратного 64, не больше,
  чем унесёт ответ запрашивающему.
- `dns.zones[].tag` и `dns.zones[].auth_keys_file` (необязательно, с v0.13.0): `"tag": "slipstream"` — фронт сам
  проверяет метку устройства в каждом запросе зоны slipstream (raycontrol `docs/spec/slipstream-v1.md` §2).
  - Устройство метки: метки имени перед зоной — base32 (RFC 4648, в любом регистре, без набивки) от поля dnsauth-v2
    (8 байт) и пакета QUIC. Поле dnsauth-v2 подписывает этот пакет. Берётся только каноничный base32: буквы и цифры
    2–7, точки где угодно, длина на целое число байт, лишние биты последнего символа нулевые — то, что сервер прочтёт
    так же (иначе метка проверялась бы над другими байтами, чем читает сервер).
  - Ключи берутся из `auth_keys_file` (абсолютный путь; как у dnstt: `<id устройства> <ключ hex>`), файл
    перечитывается при изменении. Ключ находится по подсказке, без перебора (dnsauth-v2, `required`). Файл, который не
    читается, фронт не останавливает: предупреждение в журнале, зона без ключей (всем — `NOERROR`), пока он не
    прочтётся.
  - Поле, которое уже прошло, — копия: любой на пути запроса мог бы повторять его, пока держится метка (20–30 минут), а
    сервер отправлял следующий пакет соединения на адрес копии. Фронт помнит поля прошедших запросов четыре эпохи
    (40 минут; поколения по эпохе, одна память на бэкенд: поле одной его зоны — копия и в другой). На копию — `NOERROR`
    без записей, а в первые 5 с после оригинала — ничего: это повтор резолвера, ответ оригинала уже в пути, и `NOERROR`
    его обогнал бы (`replayed` в `stats_socket`). В поколении до 524 288 полей (5–10 МиБ): это всё окно при ~870
    запросах в секунду; при большей нагрузке полное поколение начинает следующее раньше (`replay_turns`), и копии
    старше этого ловит уже сервер (он помнит взятые пакеты 30–60 с и держит горизонт ACK). Запрос, который не дошёл до
    бэкенда (его нет на связи, очередь полна), разрешает один повтор в течение 10 с (не больше 4096 таких сразу).
  - Бэкенду уходят только запросы IN TXT с одним вопросом и верной меткой, пересобранные:
    - заголовок с ID, RD и CD;
    - вопрос как пришёл (регистр сохраняется: резолверы сверяют его в ответе);
    - OPT с размером и DO запроса и без опций — если он был.
  - Остальное получает `NOERROR` без записей и до бэкенда не доходит (`untagged` в `stats_socket`). На запрос с EDNS
    в ответе OPT, как у пустого ответа сервера slipstream (4096, DO запроса, без опций): ответ фронта не отличить.
    Другой opcode, чем QUERY, получает `NOTIMP` с AA, как у dnstt.
  - Сервер slipstream (форк `arngory/slipstream`, `--front-socket`) — бэкенд в режиме `packet`. `tag` без
    `auth_keys_file` и `auth_keys_file` без `tag` — ошибка `check`; зоны одного бэкенда — все с одним `tag` и
    `auth_keys_file` или все без (зона без метки у бэкенда с меткой передавала бы запросы без проверки).
- `dns.stats_socket` (необязательно, с v0.11.0): unix-сокет со счётчиками фронта — каждому, кто подключится, одна строка JSON (`DNSFrontSnapshot`): время старта, запросы по зонам — это нагрузка, а не доходимость (имя зоны на UDP 53 может прислать кто угодно; до какой зоны доходят клиенты, видно по меченым запросам dnstt, `zones` в его `stats_socket`), отказы вне зон, ответы вершины, пробы (отвеченные и сверх темпа), поставленные в очередь бэкенда и нет (бэкенд не на связи или очередь полна), ответы бэкендов (отправленные, из них урезанные с TC; без ждущего запроса; не отправленные — нечитаемые, без вопроса, ошибка записи), датаграммы, которые не запрос. Права 0660: читают владелец и группа (rayd raycontrol). Сокет, который не создаётся, фронт не останавливает: предупреждение в журнале, счётчиков нет. Путь не должен совпадать с сокетом бэкенда, файлом ключа пробы, файлом пароля salamander или файлом ключей зоны с меткой (сравниваются пути после `filepath.Clean`): фронт удаляет то, что там лежит. С v0.13.0 REFUSED на имя вне зон несёт OPT (4096, DO запроса), если он был в запросе (RFC 6891 §7).
- `dns.zones[].ns` (необязательно, с v0.9.0): имена, на которые делегирована зона (до 8), первое — основное в SOA.
  С ними фронт сам отвечает на вершине зоны: SOA и NS — записями (TTL 300), на любой другой тип — `NOERROR` без
  записей и с SOA в authority (TTL 60, RFC 2308). Ответ больше размера запрашивающего (512 без OPT) уходит с TC и без записей. Часть резолверов без SOA и NS у вершины делегированной зоны давала
  `SERVFAIL`. Ответ собран как ответ dnstt (QR и AA, вопрос как пришёл, OPT 4096, если он был в запросе), поэтому `ns`
  ставится только зонам dnstt. Запрос не класса IN, не QUERY или с версией EDNS не 0 идёт в бэкенд, как раньше.
  С v0.11.0 имя из `ns` не может быть зоной или лежать в зоне (`ns.t.example.com` у зоны `t.example.com` — ошибка):
  запрос резолвера за его адресом фронт отдал бы туннелю, у которого адреса нет. Зона под этим именем — можно.
- Ответы бэкендов (с v0.10.0): фронт отдаёт ответ только на запрос, который его ждёт (тот же адрес клиента и ID,
  5–10 секунд), и не больше размера запрашивающего (из OPT, где бы он ни стоял в дополнительной секции; без OPT —
  512) и не больше 1232 байт, что бы ни говорил OPT; больший уходит с TC и без записей. dnstt больше и не отвечает, а
  поддельный запрос (свой OPT у него свой) получает не больше обычного ответа EDNS: ответы masterdns на пробы MTU
  (4–6 КБ) на чужой адрес больше не уходят.
- `udp.routes[]`: в каждом маршруте либо `sni` (имя из ClientHello в QUIC Initial; ClientHello может занимать
  несколько Initial, фронт собирает его), либо `salamander_password_file` (пакет снимается этим паролем и внутри —
  QUIC Initial). Бэкенд — с режимом `packet`, датаграммы идут ему как есть (для salamander — обфусцированными).
  Поток закрепляется только пакетом, который прошёл классификацию; фейки, чужие имена и мусор отбрасываются, не
  закрепляя поток. `udp.idle` — бездействие, после которого поток забывается (по умолчанию `60s`, от `5s` до `10m`).
- `tcp.routes[]`: в каждом маршруте либо `sni` (имена без учёта регистра и точки в конце, каждое — в одном маршруте),
  либо `alpn` (маршрут берётся, если клиент предлагает один из протоколов). Порядок выбора: имя, затем ALPN, затем
  `default`. Бэкенд маршрута — с режимом `fd` или `proxy-v2`. Без маршрута и без `default` соединение закрывается.
- `tcp.sniff_timeout` — сколько ждать ClientHello (по умолчанию `5s`, не больше `30s`); не TLS или тишина — закрыть
  без ответа. ClientHello может быть разбит на несколько TLS-записей (до 64 КиБ вместе).
- `tcp.window_clamp` (байты, предложение raycontrol): окно TCP в SYN-ACK на 443, чтобы клиент резал ClientHello.
  **Не реализовано**, `check` отклоняет.
- `acme_listen` — порт окна ACME. **Не реализовано**, `check` отклоняет: raycontrol выпускает сертификаты через
  DNS-01 или окно HTTP-01 на TCP 80 (решения R2-11, R4-10). В окне выпуска сертификата nftables перенаправляет на него TCP 443 от адресов
  без SPA. На этом порту фронт пропускает только ClientHello с ALPN `acme-tls/1` (в бэкенд `acme`). Остальное
  закрывает без ответа, маршруты по SNI здесь не действуют. Вне окна на порт ничего не попадает: снаружи он закрыт.
  Если сокет `acme` недоступен, соединения тоже закрываются.

## Бэкенд

```json
{
  "schema": 1,
  "role": "backend",
  "kind": "hy2-masq",
  "log": {"level": "warn"},
  "socket": "/run/niko/hy2-masq/packet.sock",
  "front_uid": 9100,
  "users_file": "/run/credentials/niko-hy2-masq.service/users.json",
  "tls": {
    "certificate_file": "/run/credentials/niko-hy2-masq.service/cert.pem",
    "key_file": "/run/credentials/niko-hy2-masq.service/key.pem",
    "curves": ["X25519MLKEM768"]
  },
  "options": {"masquerade": {"type": "proxy", "url": "https://www.example.org/", "rewrite_host": true}},
  "inner": "/run/niko/inner/vless.sock"
}
```

- `front_uid` — единственный UID, которому бэкенд отвечает (`SO_PEERCRED`).
- `tls.curves` по умолчанию `["X25519MLKEM768"]`. Другие значения `check` отвергает для `hy2-*`, `naive`, `doh`,
  `yggdrasil`.
- `inner` — потоковый unix-сокет `inner` (Xray, VLESS с `decryption`). Обязателен для `dnstt`, `masterdns`, `yggdrasil`.
- `stats_socket` (`hy2-*`, с v0.11.0 `dnstt`, с v0.15.0 `yggdrasil`; необязательно) — у dnstt: каждому, кто подключится, одна строка JSON со счётчиками бэкенда (`dnsttserver.StatsSnapshot`: время старта бэкенда — по нему видно перезапуск, — запросы, повторы из памяти, сессии и рукопожатия, отказы началам сессий (по пакетам начала: повторы клиента считаются снова) и вытеснения, отказы потокам, счётчики dnsauth и печати, а с dnsauth — `zones`: запросы каждой зоны с верной меткой устройства, по ним видно, до каких зон туннеля клиенты доходят. Это подсказка, а не доказательство: метка не покрывает зону, и кто видел запрос устройства, может повторить его в любой зоне, а повторы резолвера считаются снова; без ключа устройства или его запроса их не создать), читать нечего. Сокет, который не создаётся, бэкенд не останавливает: предупреждение в журнале, счётчиков нет; путь не должен совпадать с `socket`, `inner` или файлом, который бэкенд читает (`users_file`, `tls.certificate_file`, `tls.key_file`, `private_key_file`, `auth_keys_file`, `seal_key_file`, `obfs_password_file`; пути сравниваются после `filepath.Clean`): бэкенд удаляет то, что там лежит. У `hy2-*` — потоковый unix-сокет со статистикой сессий для замера канала
  raycontrol. Запрос — адрес клиента строкой, ответ — JSON по всем соединениям с этого адреса:
  - число соединений;
  - сглаженный RTT (минимум, медиана, максимум) и наименьший минимальный RTT;
  - отправленные и потерянные пакеты, доля потерь;
  - для соединений с Brutal — их число, темп и доля подтверждённых пакетов.

  Только суммы: за одним адресом при CGNAT бывают чужие соединения. Доступ ограничивает группа каталога сокета.

  Запрос `<адрес> <имя>` добавляет к суммам `own` — сессии пользователя `<имя>` (и его вариантов `<имя>-…`, как у
  учётных данных во время ротации) с этого адреса по одной: RTT, минимальный RTT, отправленные и потерянные пакеты и,
  если клиент задал темп, темп Brutal и доля подтверждённых. Так клиент видит свою сессию, не видя чужих.

  С v0.15.0 строка `traffic` вместо адреса — байты пользователей для лимитов трафика raycontrol
  (`docs/spec/traffic-limit-v1.md` §2.2): `{"v":1,"boot":"<16 hex>","users":{"u5":{"up":123,"down":456}}}`, затем
  сокет закрывается. `up` — сколько нода отправила назначениям, `down` — сколько получила от них и отдала клиенту:
  потоки и датаграммы, только полезная нагрузка, без заголовков Hysteria2 и QUIC. Счёт всегда включён, идёт с
  запуска процесса, чтение его не сбрасывает; `boot` случаен на каждый запуск, новый `boot` — счёт начался заново.
  В `users` — каждое имя с паролем Hysteria2 из `users_file` с запуска процесса, и снятые тоже, пока они нужны rayd:
  с v0.16.0 счётчик имени, которого в файле больше нет, удаляется, когда у имени нет ни соединений, ни потоков, ни
  сессий датаграмм и с того момента (или с выхода из файла, что позже) прошло 5 минут; проверка — при перечитывании
  и раз в 5 с. Имя, вернувшееся в файл раньше, сохраняет счётчик; удалённое и вернувшееся считается с нуля (rayd
  считает незнакомое имя с нуля). Без этого процесс, работающий месяцами, копил бы по имени на каждую ротацию
  учётных данных (raycontrol v0.23.0 даёт каждой своё имя навсегда), и ответ перерос бы предел rayd (4 МиБ, 65 536 имён). Только имя и два числа: ни назначений, ни адресов, ни портов, ни времени;
  в журнал счётчики не пишутся. Любая другая строка закрывает соединение без ответа, как раньше; так же отвечает на
  `traffic` niko-server до v0.15.0. Пределы те же, что у запроса адреса: строка до 192 байт, 2 с на всё.

  У `yggdrasil` — как у dnstt, одна строка JSON (`YggdrasilSnapshot`): `started` — время старта бэкенда,
  `dropped_frames` — кадры traffic, pathNotify, pathBroken и pathLookup на линке клиента между ним и не узлом (и не
  своей группой LAN), отброшенные фильтром, а с v0.16.0 и lookup группы к узлу на пути к клиенту (raycontrol
  `lan-v1` §2.2, `docs/SPEC.md` §3.4). С v0.16.0 ещё `relayed_frames` и `relayed_bytes` — кадры, которые узел
  переслал для группы, и их длина (тип и тело, как их списало ведро: один раз, чаще всего на выходе к устройству
  группы), и `relay_dropped_frames` — отброшенные сверх `lan_relay_mbps` группы (при 0 — все). Только суммы: чьи
  кадры, не видно нигде, в журнале тоже.

  С v0.16.0 сокет `yggdrasil` отвечает и на строку `traffic`, как Hysteria2: `{"v":1,"boot":"<16 hex>","users":{"u5":
  {"up":123,"down":0}}}`. Ключ — группа LAN (`yggdrasil.lan`, имя пользователя raycontrol), `up` — байты кадров,
  которые узел переслал для группы, по длине кадра, один раз, там, где их списало ведро (`docs/SPEC.md` §3.4);
  `down` всегда 0.
  Пересылка идёт мимо `inner`, её Xray не видит: так она попадает в лимит трафика (raycontrol
  `docs/spec/traffic-limit-v1.md` §2.2, `lan-v1` §4.4). Группы из файла видны с первого чтения, с нулём тоже; группа,
  которой в файле больше нет, удаляется, когда 5 минут после выхода из файла и после последнего пересланного кадра
  прошли (как имена Hysteria2). `boot` случаен на каждый запуск. Всё прочее — другая строка, конец ввода (половинное
  закрытие) или ничего за 0,5 с — получает снимок, как раньше: кто читает снимок, не ждёт, если сразу закроет запись.
  Строка до 192 байт, 2 с на всё.

## Файл пользователей (`users_file`)

raycontrol пишет отдельный файл для каждого бэкенда, только с учётными данными его `kind` (минимум прав).
Бэкенд не должен рассчитывать на поля других видов.

Один формат для всех видов. Неизвестные поля игнорируются. Пользователь без учётных данных для этого `kind`
пропускается.

```json
{
  "users": [
    {"name": "u-17", "enabled": true,
     "hy2": {"password": "…"},
     "naive": {"username": "…", "password": "…"},
     "yggdrasil": {"public_key": "<64 hex>", "lan": "u17"}}
  ]
}
```

`yggdrasil.lan` (с v0.16.0, необязательно) — группа LAN ключа (raycontrol `docs/spec/lan-v1.md` §2.2): базовое имя
пользователя raycontrol `u<id>`, 1–32 символа `[a-z0-9-]`. Нет поля или `""` — группы нет. Ключи одной группы
(устройства одного пользователя, показавшие себя) достают друг до друга через узел; ключ без группы — только до узла.
Неверное значение, как и неверный ключ, отвергает весь файл (бэкенд остаётся с прежним), так же ключ, записанный
дважды с разными группами. Ключ узла ни в какой группе не бывает, что бы ни было в файле.

Пользователи Hysteria2 выходят только на публичные адреса. Переменная окружения
`NIKO_SERVER_UNSAFE_ANY_DESTINATION=1` снимает это ограничение — только для тестов на одном хосте; raycontrol её
не задаёт, бэкенд при ней пишет предупреждение.

Бэкенды Hysteria2 перечитывают файл по `SIGHUP` и сами, когда он меняется (проверка раз в 5 с). Соединения имён,
у которых пароль остался тем же, не рвутся. С v0.15.0 QUIC-соединения имени, которого в файле больше нет или которое
выключено (`enabled: false`: просрочен, выключен, исчерпал лимит), и соединения, вошедшие с прежним паролем имени,
закрываются сразу, со всеми потоками и датаграммами (raycontrol `docs/spec/traffic-limit-v1.md` §3.2); раньше пароль
проверялся раз на соединение, и снятый пользователь оставался, пока его клиент держит соединение. Соединение, чей
пароль сверялся со старой таблицей, пока шло перечитывание, тоже закрывается. Бэкенд `yggdrasil` перечитывает так
же; линки ключей, которых больше нет в файле, закрываются сразу.
С v0.15.0 клиент `yggdrasil` достаёт только до узла: кадры между ним и другими клиентами (своими и чужими) или общей
сетью бэкенд отбрасывает (`docs/SPEC.md` §3.4). С v0.16.0 — ещё до ключей своей группы `yggdrasil.lan`. Смена группы
ключа при перечитывании линк не рвёт: фильтр видит новую группу со следующего чтения линка; рвёт только удаление ключа.

Пары «текущие + следующие» для ротации: raycontrol кладёт в файл обе записи, например с именами
`u-17` и `u-17@next`. Бэкенд принимает обе до следующего `SIGHUP`.
