# IPC фронт ↔ бэкенд (версия 1, черновик)

Черновик для согласования с raycontrol, замораживается на R1. Обе стороны реализует niko-server.
Все целые числа — big-endian.

## Сокеты и права

Правило: **процесс, который подключается к сокету другого процесса, входит в его группу** (`SupplementaryGroups=`).
Больше ни у кого доступа нет.

- `/run/niko` — `0755`, владелец root (`tmpfiles.d`).
- У каждого процесса, который слушает, свой каталог: `/run/niko/<имя>/`. Его создаёт systemd
  (`RuntimeDirectory=niko/<имя>`, `RuntimeDirectoryMode=0710`) с владельцем и группой процесса. Группа получает
  только право прохода в каталог.
- Сокет создаёт сам процесс внутри своего каталога и сразу ставит права `0660`, группа — его собственная.
- Кто к кому подключается:
  - фронт входит в группы всех бэкендов и Xray;
  - Xray входит в группу `site` (цель REALITY);
  - `dnstt`, `masterdns`, `yggdrasil` и движки белых списков входят в группу `inner`.
- Проверка собеседника при `connect`/`accept` — `SO_PEERCRED`, в обе стороны:
  - бэкенд сверяет UID с `front_uid`;
  - фронт сверяет UID с `uid` бэкенда из своего конфига.
- Соединения фронта с бэкендами niko-server — `SOCK_SEQPACKET`: границы сообщений сохраняются, ответный файл сокета
  не нужен. Сокеты Xray (`xray-reality/reality.sock`, `inner/vless.sock`) и `site/tls.sock` — обычные `SOCK_STREAM`,
  по одному соединению на поток.
- Буферы: `SO_SNDBUF`/`SO_RCVBUF` 4 МиБ на соединениях режима `packet`.
- Переподключение: фронт держит одно соединение с каждым бэкендом и при разрыве или отсутствии бэкенда
  переподключается с задержкой (100 мс, удваивается до 5 с). Датаграммы, пришедшие, пока соединения нет,
  отбрасываются. Фронт стартует и без бэкендов (порядок юнитов: `inner` → бэкенды → фронт, но не обязателен).

## TCP, режим `fd`

Бэкенд слушает `SOCK_SEQPACKET` (`/run/niko/<backend>/fd.sock`). Фронт держит одно соединение на бэкенд
и переподключается при разрыве. На каждое
принятое TCP-соединение фронт отправляет одно сообщение: ancillary `SCM_RIGHTS` с одним дескриптором и полезную
нагрузку:

| Поле | Размер | Значение |
|---|---|---|
| magic | 4 | `NKT1` |
| flags | 1 | 0 |
| route_len | 1 | длина имени маршрута |
| route | route_len | имя бэкенда из конфига (для логов) |
| src | 19 | адрес клиента: семейство (1: 4 или 6) + адрес (16, IPv4 — в форме `::ffff:a.b.c.d`) + порт (2) |
| dst | 19 | локальный адрес сокета, тот же формат |
| sni_len | 1 | длина SNI |
| sni | sni_len | SNI из ClientHello (может быть пустым) |
| prefetch_len | 4 | сколько байт фронт уже прочитал |
| prefetch | prefetch_len | эти байты (первый TLS-рекорд, до 16 КБ) |

Пример реализации стороны бэкенда — `nikoserver.ListenFD` (`net.Listener`, чьи соединения — переданные сокеты,
`RemoteAddr` — `src`). Фронт держит одно соединение на бэкенд; если его нет, принятое TCP-соединение закрывается.

После отправки фронт закрывает свою копию дескриптора. Бэкенд оборачивает сокет так, что сначала читаются
байты `prefetch`, затем сам сокет (`bufio.CachedConn`). Неверное сообщение — бэкенд закрывает присланный дескриптор
и пишет ошибку. Подтверждений нет.

## TCP, режим `proxy-v2` (Xray)

Фронт открывает поток к unix-сокету Xray на каждое соединение и пишет:
1. заголовок PROXY v2 (`PROXY` + адреса клиента и локальный, команда `PROXY`);
2. байты `prefetch`;
3. дальше копирует поток в обе стороны.

Xray: `listen` — путь сокета, `sockopt.acceptProxyProtocol: true`.

## UDP, режим `packet`

Бэкенд слушает `SOCK_SEQPACKET` (`/run/niko/<backend>/packet.sock`). Фронт держит с ним одно соединение. Каждое
сообщение в обе стороны — одна датаграмма:

| Поле | Размер | Значение |
|---|---|---|
| magic | 2 | `NU` |
| version | 1 | 1 |
| client | 19 | адрес клиента (как `src` выше); в ответе — кому отправить |
| local | 19 | локальный адрес UDP-сокета фронта, на который пришёл пакет; в ответе — с какого отправить |
| payload | остаток | датаграмма как есть (для `hy2-obfs` — с обфускацией salamander, бэкенд снимает её сам) |

- Бэкенд видит это как `net.PacketConn`: `ReadFrom` возвращает `client`, а `WriteTo(client)` пишет ответ с тем же
  `local`.
- Обе стороны пишут неблокирующе. Если буфер полон (`EAGAIN`), датаграмма отбрасывается, как у UDP.
  Соединение при этом не рвётся.
- Поток (`client`, `local`) живёт во фронте до 60 с бездействия. Новый поток классифицируется заново.

**Версия 2 (с v0.14.0): устройство запроса.** Бэкенду с `"devices": true` (только бэкенд зоны с меткой, `slipstream`)
фронт шлёт запросы в версии 2: после `local` — 8 байт устройства, чью метку он проверил, потом датаграмма. Ответы
бэкенда остаются в версии 1.

| Поле | Размер | Значение |
|---|---|---|
| magic | 2 | `NU` |
| version | 1 | 2 |
| client, local | 19 + 19 | как в версии 1 |
| device | 8 | жетон устройства: первые 8 байт SHA-256 от `niko-server device\0<id устройства>` (id — из файла ключей зоны); один для всех запросов устройства, сам id не виден |
| payload | остаток | запрос как его собрал фронт |

По жетону сервер slipstream считает соединения устройства (`--max-connections-per-device`, server-v0.2.0): ключ одного
устройства не займёт все места сервера.

## Запасной путь

Если копия UDP через фронт окажется узким местом (нагрузочный тест, [`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md) §4):
каждый UDP-бэкенд открывает свой сокет на 443 с `SO_REUSEPORT`, а программа eBPF (`SO_ATTACH_REUSEPORT_EBPF`)
выбирает сокет по тем же правилам, что udpmux (SNI из QUIC Initial, salamander). Заголовок UDP тогда не нужен,
TCP не меняется.
