# niko-server: спецификация

niko-server — data plane и «наше ядро»: обслуживает протоколы клиента Niko. Управляет им raycontrol (control plane):
хранит пользователей и ключи, генерирует конфиги niko-server и Xray, ведёт nftables и SPA, ротирует ключи,
отдаёт подписку и API. Решения raycontrol главнее этого документа: при расхождении действует
[`docs/decisions.md`](https://github.com/arngory/raycontrol/blob/main/docs/decisions.md).

Ответы на вопросы raycontrol и черновики контрактов: [`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md), [`CONFIG.md`](CONFIG.md), [`IPC.md`](IPC.md).

Что уже есть в форке sing-box:

- всё собирается из наших форков, сторонних бинарников нет;

- release notes по одной строке на правку: сначала английские строки, потом те же на русском;
- после каждого законченного блока — релиз.

## 1. Цель

Нода обслуживает все протоколы клиента на одном IP. Работают отдельные процессы:

| Процесс | Что делает | Права |
|---|---|---|
| `niko-server front` | мультиплексоры TCP 443, UDP 443, UDP 53; знает только таблицу маршрутов, пароль salamander и сокеты бэкендов, ключей пользователей не знает | только `CAP_NET_BIND_SERVICE` |
| `niko-server backend` (по одному на протокол) | `hy2-masq`, `hy2-obfs`, `naive`, `doh`, `dnstt`, `masterdns`, `yggdrasil`, `inner`, `site` | без capabilities, только свой unix-сокет |
| Xray | REALITY (и `inner`, пока в форке нет сервера VLESS encryption) | без capabilities, unix-сокет |
| `rayspa` (raycontrol) | приём SPA v2 через NFLOG, ведение nftables | `CAP_NET_ADMIN` |

У каждого процесса свой системный пользователь с фиксированным UID (правила nftables по `skuid`).

**Периметр.** Все порты закрыты (nftables, policy `drop`). Доступ — только после SPA v2 и только к портам из scope
устройства, на TTL. Для всех открыты лишь:

| Порт | Кому | Что |
|---|---|---|
| UDP 53 | всем | dnstt и MasterDnsVPN в своих делегированных зонах, остальное — `REFUSED` |
| TCP 443 | всем, только на время выпуска сертификата | только ACME (TLS-ALPN-01): nftables перенаправляет адреса без SPA на отдельный порт фронта, там проходит лишь ALPN `acme-tls/1` (§3.1) |
| TCP 443, UDP 443 | после SPA v2 | всё остальное (§2) |
| UDP, порт слота SPA | всем | `rayspa`, порт ротируется по слотам |

TCP 80 и TCP/UDP 853 не открываются. Port-knocking не используется. Неавторизованный адрес получает drop,
а не приманку.

## 2. Архитектура

```
                        nftables: drop, кроме UDP 53, порта SPA и окна ACME; allow-наборы от rayspa
TCP 443 ──► front/tcpmux ─┬─ SNI <r>.example.com ──► unix + PROXY v2 ──► Xray REALITY
                          ├─ SNI <n>.example.com ──► SCM_RIGHTS ──► backend naive / doh
                          ├─ SNI <y>.example.com ──► SCM_RIGHTS ──► backend yggdrasil (tls-линк)
                          ├─ (адрес без SPA, окно ACME) ──► acme_listen: только ALPN acme-tls/1 ──► ACME
                          └─ остальное           ──► как <r> (REALITY уведёт в приманку site)
UDP 443 ──► front/udpmux ─┬─ QUIC, SNI <h>.example.com ──► backend hy2-masq
                          ├─ QUIC, SNI <n>.example.com ──► backend naive (QUIC) / doh (HTTP/3)
                          ├─ salamander             ──► backend hy2-obfs
                          └─ остальное              ──► drop
UDP 53  ──► front/dnsmux ─┬─ *.<t>.example.com ──► backend dnstt     ──► inner
                          ├─ *.<v>.example.com ──► backend masterdns ──► inner
                          └─ остальное         ──► REFUSED
```

Связь фронта с бэкендами — unix-сокеты, формат — в [`IPC.md`](IPC.md):
- **TCP:** фронт передаёт принятый сокет бэкенду через `SCM_RIGHTS` вместе с метаданными (адрес клиента, уже
  прочитанные байты, маршрут). Xray получает поток через свой unix-сокет с заголовком PROXY v2.
- **UDP:** фронт пересылает датаграммы бэкенду по соединению `SOCK_SEQPACKET` с заголовком «адрес клиента»; бэкенд
  видит виртуальный `net.PacketConn`. Ответы идут обратно по тому же соединению через фронт.
- Сокет каждого процесса лежит в его каталоге `/run/niko/<имя>/`. Доступ есть только у тех, кто входит в его группу.
  Обе стороны сверяют `SO_PEERCRED`. Правила — в [`IPC.md`](IPC.md).

### 2.1. Почему REALITY отдаётся Xray

- Xray — эталон REALITY: `mldsa65Seed`, `minClientVer`, правильная работа с гибридным X25519MLKEM768.
  `sagernet/reality` в sing-box отстаёт.
- Xray слушает unix-сокет с `acceptProxyProtocol`. Фронт пишет туда заголовок PROXY v2, затем уже прочитанные
  байты ClientHello, затем остальной поток.

### 2.2. Домены

- Поддомены (`<r>`, `<n>`, `<h>`, `<y>`, зоны туннелей `<t>`, `<v>`) выбираются случайно при установке и ротируются
  через raycontrol. В тексте ниже они обозначены угловыми скобками.
- DNS: wildcard `*.example.com A <IP>` и NS-делегирование зон туннелей. Записи ведутся вручную, `check` их проверяет.
- Сертификаты: если у DNS-провайдера есть API — wildcard через DNS-01; иначе поддомены через короткое окно ACME
  и редкая ротация SNI (много выпущенных поддоменов в журналах CT — сам по себе отпечаток).
- REALITY в режиме self-steal: `target` — бэкенд `site` (генерируемый правдоподобный сайт с настоящим сертификатом
  `<r>.example.com`, TLS 1.3 + h2).
- Вариант «домена нет» (REALITY с чужим `target`) не поддерживается: раньше он запрещал naive и DoH на том же IP,
  а случайные поддомены его заменяют.

## 3. Компоненты

### 3.1. tcpmux (TCP 443)

- Читает первый TLS-рекорд (до 16 КБ, таймаут 5 с), достаёт SNI и ALPN (`common/sniff`).
- Таблица маршрутов SNI → бэкенд — из конфига фронта. Без SNI и с неизвестным SNI — маршрут `default` (REALITY).
- Не TLS: закрыть соединение без ответа.
- **Окно ACME (TLS-ALPN-01).** nftables не видит ALPN, поэтому открывать 443 целиком нельзя: сканер, следящий за
  журналами CT, в это время дошёл бы до naive, Yggdrasil и REALITY без SPA. На время окна `rayspa` добавляет правило
  `tcp dport 443` от адресов вне allow-наборов → `redirect to :<acme_listen>`. На этом порту фронт пропускает только
  ClientHello с ALPN `acme-tls/1` (в бэкенд `acme`), остальное закрывает без ответа. Адреса с SPA идут на обычный
  443, как всегда. Если у DNS-провайдера есть API, предпочтителен DNS-01: окно не нужно вовсе.
- Неавторизованных адресов до фронта не пропускает nftables. Приманка остаётся для тех, кто прошёл SPA:
  за одним адресом CGNAT может быть и проверяющий, поэтому сервисы должны выдерживать активное зондирование сами.

### 3.2. udpmux (UDP 443)

Один сокет, разбор по потокам (адрес:порт клиента). Классификация по первому пакету потока, запоминается до `udp.idle`
бездействия (по умолчанию 60 с):

1. **QUIC long header с известной версией.** Расшифровать Initial на initial-ключах (QUIC-сниффер sing-box),
   достать SNI, выбрать бэкенд. Initial клиента в датаграмме меньше 1200 байт отбрасывается (RFC 9000 §14.1).
   ClientHello собирается из CRYPTO-кадров по смещениям, из нескольких Initial в любом порядке (первый полёт Chromium
   с постквантовым ClientHello — два пакета; клиент может слать их в обратном порядке). Целый ClientHello в одном
   пакете не оставляет состояния: с именем, которое здесь есть, поток закрепляется, с чужим — пакет отбрасывается, и
   поток остаётся свободным. Несобранный ClientHello ждёт (так с v0.18.1):
   - 3 с от первого такого пакета потока (проверяется и при следующем пакете, не только раз в несколько секунд);
   - не больше 4 Connection ID на поток (у каждого фейка может быть свой; когда места нет, уходит самый старый, а не
     новый: настоящий полёт идёт после фейков), не больше 16 пакетов на ID; CRYPTO-кадров не больше 32 в пакете
     (Chromium добавляет до 10 дроблений) и 256 кусков на ClientHello (соседние куски склеиваются);
     перекрывающиеся кадры должны совпадать, иначе
     ClientHello отбрасывается (бэкенд получит пакеты как есть, и имя, по которому фронт ведёт, должно быть тем, что
     он прочтёт);
   - не больше 4096 потоков и около 16 МиБ на все вместе по учёту (в куче — до 20 МиБ: размеры аллокатора и сами
     потоки в учёт не входят): датаграммы целиком, CRYPTO-данные — сколько пришло, а не буфер до старшего смещения, —
     и накладные расходы. Сверх любого из пределов уходят самые старые потоки, а не
     новый: Initial может сделать кто угодно (ключи берутся из пакета), и чтобы вытеснить настоящего клиента, потоп
     должен прислать 4096 новых потоков (около 4,9 МБ Initial по 1200 байт) между двумя пакетами его первого полёта,
     а они идут подряд.

   Закреплённые потоки (v0.18.1): не больше 262144, до `udp.idle` простоя (по умолчанию 60 с). Поток, закреплённый
   по Initial или по метке с нового адреса, сначала не подтверждён: это может прислать кто угодно с любого адреса.
   Подтверждает его пакет клиента на connection ID сервера — тот, что первый ответ бэкенда в длинном заголовке назвал
   своим (Source Connection ID; знает его только тот, кто ответ получил). Проверяются 16 датаграмм клиента после этого
   ответа. До ответа фронт запоминает ID, которые выбрал клиент (Destination Connection ID его длинных заголовков), не
   больше двух: датаграммы на них не считаются (они ушли раньше ответа), а ответ, который называет своим один из них
   (так отказывает quic-go), ничего не подтверждает; с третьим ID поток остаётся неподтверждённым. Так у Chromium: он
   остаётся на ID сервера. Подтверждённых потоков с одного источника (адрес IPv4, /48 IPv6) — не больше 1024, сверх —
   поток остаётся в очереди (и подтвердится, когда место освободится): иначе хост со своей /64 подтвердил бы всю
   таблицу, по настоящему рукопожатию на поток, и закрыл бы новые потоки. Подтверждённый поток, которому бэкенд не
   отвечал `udp.idle`/2, снова встаёт в очередь первым на выход и подтверждается заново, только если бэкенд ответил
   за `udp.idle`/2 или после прошлой датаграммы клиента: иначе таблицу держали бы датаграммы, на которые не отвечает ни один бэкенд.

   То, что шлёт бэкенд, поток не подтверждает: сервер quic-go шлёт больше трёх раз против присланного (до датаграммы
   сверх предела на каждое соединение, а потоку достаются все соединения с его адреса; пробы пути на новый адрес),
   читает адрес ответы или нет. Метка тоже не подтверждает: настоящий ID с меткой бэкенда получает любой, кто к нему
   подключится. Клиенты на quic-go сразу после рукопожатия переходят на ID из зашифрованного NEW_CONNECTION_ID и
   остаются неподтверждёнными: если их поток уйдёт, следующий же пакет закрепит его заново по метке (raycontrol
   включает метки всем QUIC-бэкендам). Без меток такой поток после ухода не восстановится.

   Неподтверждённые потоки стоят в очереди по последней датаграмме клиента. Когда таблица полна, новый поток занимает
   место того, чей клиент молчит дольше всех; если подтверждены все, новый не закрепляется, как раньше, и его пакеты
   разбираются по одному. Закрепление стоит Initial в 1200 байт (под salamander — 1208) или пакета с меткой от 29 байт:
   вытеснить всю очередь можно и за 7,6 МБ, но с метками ушедший поток возвращается первым же пакетом клиента. Если
   источник клиента исчерпал долю закреплений по метке (32 в секунду после 128), ушедший поток ждёт, пока она
   восстановится: тот, кто знает адрес клиента, может выбирать её пакетами с подделанным адресом.

   Пробы пути quic-go — короткий заголовок, дополненный ровно до 1200 байт (под salamander — 1208): PATH_CHALLENGE на
   новый адрес и PATH_RESPONSE на каждый PATH_CHALLENGE с него, сверх трёх раз, которые допускает RFC 9000 §8.2.1. На
   поток они уходят не больше чем втрое против того, что прислал его клиент, считая вместе с пробами длинные заголовки
   бэкенда (рукопожатия на потоке и их повторы, которые адрес получает, читает он или нет; под salamander, где для
   этого датаграмму нужно открыть ключом, — среди первых 32 датаграмм бэкенда потоку и снова после каждого длинного
   заголовка клиента от 1208 байт), и так же на подтверждённый. Сверх этого — одна
   проба на поток: в пределах трёх раз против того, что прислали все потоки его источника (адрес IPv4, /64 IPv6), не
   больше 32 в секунду с источника (запас 128), а если этого мало — не больше 2 в секунду с источника (запас 8) и 256
   в секунду со всех (запас 1024). Так клиент, сменивший порт (NAT, прыжки портов Hysteria2) или адрес, получает
   PATH_CHALLENGE сервера сразу, сколько бы клиентов ни делили его адрес (quic-go от sagernet шлёт следующий, только
   когда сочтёт первый потерянным, через секунду-две). Подделав загруженный адрес, на него не вытянуть больше 32
   таких проб в секунду, закрепляя потоки хоть по метке, хоть по Initial. На адрес без потока
   проба не уходит вовсе. Иначе пакет чужого соединения с поддельного адреса, прошедший по метке, делал из 31 байта
   1200 на этот адрес (с v0.18.0). Обычный ответ ровно такого размера с коротким заголовком считается пробой: пакеты
   quic-go другого размера (1280 и больше), но поток данных ровно в 1200 байт сверх трёх раз потеряет лишнее.
2. **Salamander.** 8 байт соли + (нагрузка XOR поток `BLAKE2b-256(пароль ‖ соль)`). Снять обфускацию паролем
   из конфига фронта; если внутри QUIC long header с известной версией — поток `hy2-obfs`. С v0.19.3 у маршрута может
   быть список паролей, свой у каждого устройства (`salamander_passwords_file`, raycontrol
   `docs/spec/salamander-device-v1.md`): фронт пробует ключи (сначала ключи источника, своим бюджетом, затем весь
   остаток списка или ничего — бюджет попыток превращает исчерпание CPU в предел доступности новых потоков; метка из
   остатка закрепляет только со второй датаграммы), снимает salamander сам и отдаёт бэкенду обычный QUIC, а ответы
   закрывает ключом потока и только на поток своего бэкенда; повтор соли Initial, и со своего адреса, — drop.
   Перебор идёт в горутине чтения сокета, не больше ~0,15 с ядра в секунду. Бэкенд такого маршрута — только в нём.
   Подробно и цифры — `CONFIG.md`.
3. **Connection ID с меткой (v0.18.0,** raycontrol `docs/spec/quic-cid-route-v1.md`**).** Короткий заголовок или
   Handshake с connection ID в 8 байт — открытый или под salamander пароля маршрута: расшифровать ключом каждой
   метки бэкендов этого вида (Speck64/128, свой ключ у метки; ключи — в `udp.cid_keys_file`, секрета ноды у фронта
   нет); метка сошлась — поток бэкенда. Так соединение
   переживает смену адреса клиента (NAT rebinding, переход на новый сокет при смене слота). Не больше 32 таких
   потоков в секунду с источника. Бэкенды Hysteria2 переходят на новый адрес только после проверки пути.
4. Иначе — drop. **Поток по такому пакету не запоминается**: закрепляется только первый пакет, прошедший классификацию. Клиент может слать перед настоящими пакетами фейки (случайные или QUIC Initial с чужим SNI), и они не должны закреплять поток за drop ([`../research/anti-dpi.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/research/anti-dpi.md) §3).

SPA в udpmux нет: SPA v2 принимает `rayspa` на отдельном ротируемом порту (§3.5).

Hysteria2 принимает готовый `net.PacketConn` (виртуальный, от IPC) без патча: `hysteria2.Service.Start(conn)` из
sing-quic. Бэкенды `hy2-masq` и `hy2-obfs` — niko-server на sing-quic.

Два конфига Hysteria2 — два бэкенда:
- `hy2-masq`: TLS с сертификатом `<h>.example.com` и `masquerade`;
- `hy2-obfs`: `obfs.type = salamander`, самоподписанный сертификат; клиент пинит его публичный ключ
  («Настройки соединения → Пиннинг сертификата», не `pinSHA256`).

**Постквант.** У `hy2-obfs` TLS `CurvePreferences = [X25519MLKEM768]`, без отката на классические группы. У
`hy2-masq` с v0.19.3 рукопожатие — как у сайта на том же адресе: группы Go по умолчанию, `X25519MLKEM768` первой (TLS
1.3: в QUIC другого нет), а пароль сверяется только на соединении с `X25519MLKEM768` (`AuthCurve` в sing-quic,
`ConnectionState.CurveID`); на любом другом запрос авторизации получает маскировку, как с неверным паролем. Раньше
рукопожатие без ML-KEM не проходило, и зонд без ML-KEM (сосед по CGNAT с допуском SPA, подмена адреса на пути)
отличал имя hy2-masq, naive-quic и DoH3 от сайта под тем же сертификатом (ревью протоколов 2026-11-21, M3; naive и DoH
так же меняются в raycontrol v0.36.1). Трафик пользователей остаётся постквантовым. За salamander рукопожатия без
ключа никто не видит: у `hy2-obfs` — как было.

**Простой и keepalive (v0.18.2).** QUIC idle — 60 с (`hysteriaIdle`), keepalive сервера — 28 с
(`hysteriaKeepAlive`, `hysteriaQUICOptions`), а не 10 с по умолчанию sing-quic. В quic-go сторона пингует через
min(свой keepalive, idle/2) после последнего полученного пакета. PING сервера каждые 10 с, на который клиент сразу
отвечал, сбрасывал таймер клиента до срабатывания: телефон в покое просыпался 360 раз в час по инициативе сервера,
какой бы keepalive клиент ни просил. Теперь клиент, который пингует раз в 25 с (Niko) или чаще (умолчание Hysteria —
10 с), сбрасывает таймер сервера первым, если его круговая задержка с задержкой ACK меньше 3 с, и сервер его не
пингует. Замолчавшему клиенту сервер шлёт PING раз в 28 с, и ответ клиента держит соединение и его NAT-привязку. Это
телефон, у которого заснул процессор: таймеры Go идут по CLOCK_MONOTONIC, а он не считает время сна, а AlarmManager и
wakelock для keepalive Niko не держит. Иначе такой телефон через 60 с терял бы соединение, а под salamander, где
stateless reset нет, его следующие запросы ждали бы целый простой. 28 с, а не idle/2: PING уходит через 28 с после
прихода последнего ACK телефона и должен успеть до конца NAT-привязки в 30 с, которую этот ACK продлил (бывает у
мобильных сетей; RFC 4787 просит 2 мин). Это так при круговой задержке меньше 2 с. Сервер отвечает ACK на каждый
PING клиента: при keepalive клиента меньше половины `udp.idle` (у raycontrol `udp.idle` — 150 с) бэкенд
подтверждённого потока во фронте не молчит дольше idle/2 (§3.2).

**Пределы соединений на пользователя (v0.17.0;** raycontrol `docs/spec/conn-limit-v1.md` §2, §3.2, §5**).** Модель та
же, что у `rayd naive` (raycontrol v0.24.0), на пользователя (базовое имя: `u5` для всех его учётных данных) в
процессе бэкенда:
- TCP — в `outbound.NewConnectionEx` до dial: место (1024 сразу), токен попытки (30/с, запас 600, ожидание до 0,5 с и
  не дольше потока), долг неудачных dial (5/с, запас 100). Отказ — TCP-ответ Hysteria2 `too many connections`; текст
  сверяет клиент. Имя идёт через кеш имён процесса (промах — токен резолва: 20/с, запас 100), адреса нода перебирает
  сама: каждый — попытка, неудача с ушедшим SYN — в долг.
- UDP — в `relayUDP` до сокета: место сессии (256), на пределе уступает самая тихая (10 с без пакетов в обе
  стороны). Пары (порт сессии, назначение) живут, как записи conntrack (30 с без ответа, 120 с с ответом), после
  конца сессии — в журнале пользователя; потолок 1024 на пользователя и четверть `nf_conntrack_max` на процесс. Новые
  назначения — 100/с, запас 200. Сверх — датаграмма отбрасывается. Отказ сессии, который клиент повторяет каждой
  датаграммой, не стоит сокета и считается раз на номер сессии.
- QUIC — `MaxConcurrentStreams` 2048 вместо 2⁶⁰: выше предела TCP, чтобы первым приходил отказ с причиной.
- С v0.19.3: QUIC-соединений пользователя сразу — 16. На пределе новому уступает (то, от которого дольше всех не
  было пакетов): соединение его же учётных данных (устройство переподключилось); иначе — соединение пользователя, не
  слышное 35 с (keepalive 28 с и счёт раз в 5 с); иначе — соединение учётных данных, у которых их больше всех, если
  их больше честной доли: предела, делённого на число учётных данных с соединениями вместе с новыми, не меньше
  одного. Учётные данные — это устройство (raycontrol даёт их каждому), так что утёкшая ссылка с 16 живыми
  соединениями уступает устройствам владельца места до равной доли и ничего у них не берёт. Иначе — все учётные
  данные в своей доле и слышны — новое соединение закрывается до ответа авторизации (хук соединения в вендоренном
  sing-quic отвечает «нет» раньше 233), клиент видит закрытие без кода ошибки; клиенты Hysteria2 переподключаются. Все случаи — вид
  `conns`. Живые соединения разных учётных записей не вытесняют друг друга по кругу: новое в своей доле заменяет своё. Два клиента одной учётной записи (общая ссылка), урезанной шагом 3 ниже их числа, вытесняют друг друга при каждом переподключении. Потоков, ждущих TCP-запроса, — 1024 у пользователя (вид `pending`), и
  каждый ждёт его не дольше 10 с; до типа первого кадра и HTTP-запрос до ответа читаются по 64 потока соединения, тоже
  до 10 с, до пароля и после (ревью протоколов 2026-11-21, M2). Датаграммы клиента в сессии ждут чтения не больше
  128 КиБ (раньше — 64 сообщения любого размера, собранное — до 64 КиБ), фрагменты держатся не больше чем у двух
  незаконченных пакетов сессии (раньше — до 65 536 пакетов по 10 с), пакет, чьи фрагменты держат больше 96 КиБ,
  отбрасывается (число фрагментов — клиента: длинное назначение в заголовке и малый MTU его растят). Каждое
  сообщение считается по тому, что держит: всю датаграмму, из которой оно разобрано, и строку назначения, а не одни
  данные; назначение длиннее 300 байт (имя 255 и порт; зона IPv6-адреса в Linux — до 15 символов, а разбор адреса
  пропустил бы зону в килобайт) — не сообщение, соединение закрывается. Раньше 255 фрагментов без данных с длинным
  назначением по 1,4 КБ держали около 360 КБ на пакет при счёте ноль. Два запроса авторизации одного соединения
  сразу делают его пользователя один раз: второй получает ответ «уже авторизовано».

- Отказы — в строке `traffic` сокета статистики (`limit`, по базовому имени и виду), выключатель — `conn_limit` и
  `conn_limit_file` ([`CONFIG.md`](CONFIG.md)). В журнале — только `too many connections` на `debug`, без имени и
  назначения.


**Память соединений (v0.19.3; ревью протоколов 2026-11-21, M2).** quic-go держит присланное клиентом, пока его не
прочтёт сервер, — до окна приёма, и отправленное, пока клиент не подтвердит, — до окна перегрузки. Раньше окна приёма
начинались с максимума Hysteria2 (8 МиБ на поток, 20 МиБ на соединение), а окно Brutal — темп клиента на сглаженный
RTT, который клиент раздувает, задерживая ACK, до 40 000 пакетов quic-go в полёте (около 56 МиБ); соединений у
пользователя — сколько пропустит фронт. Выгрузка к назначению, которое не читает, или загрузка с поздними ACK держали
20–56 МиБ на соединение. Теперь (`nikoserver/hymem.go`):
- окна приёма начинаются с окон quic-go (512 КиБ поток, 768 КиБ соединение, как у naive-quic) и растут настройкой
  quic-go, пока читающий успевает, до 8 и 20 МиБ; каждый байт роста окна соединения берётся из бюджета процесса
  (`AllowConnectionWindowIncrease`) в пределах доли пользователя и возвращается, когда соединение кончается: окно
  quic-go не сужает. Окна берут не больше половины бюджета и половины доли: долгая выгрузка не держит то, что нужно
  загрузкам пользователя, всё время соединения;
- в полёте у соединения после пароля — не больше 1 МиБ плюс взятое из того же бюджета, до окна Brutal или BBR;
  берётся шагами (256 КиБ или четверть, что больше; не хватило — следующая просьба не раньше чем через 20 мс). Когда
  бюджета или доли не хватает, остальные соединения отдают взятое сверх своего окна и своего полёта, а не
  отправлявшие секунду пакетов, ждущих ACK, — сверх полёта. Полёт, который клиент не подтверждает, — занятая память:
  он остаётся в счёте, сколько бы отправка ни стояла;
- бюджет — от памяти процесса (§4, «Память процесса»): с пределом cgroup ниже хоста — 3/8 предела `L` своего юнита
  (у каждого бэкенда Hysteria2 свой юнит и свой предел), не больше 2 ГиБ; без предела — восьмая часть `MemTotal`, от
  32 МиБ до 2 ГиБ, как до v0.19.3 (восьмая, а не четверть: бэкендов Hysteria2 на ноде два, у каждого свой). Доля
  пользователя — восьмая часть бюджета; неавторизованные — один пользователь. В журнал — одно предупреждение, когда
  впервые не хватило бюджета, и одно — доли, без имён. Поля в конфиге нет;
- полы соединений — внутри бюджета, когда у процесса есть предел cgroup (решение владельца, raycontrol memory-v1
  §9 п. 6): соединение с верным паролем берёт свой пол, 1 МиБ полёта + 768 КиБ окна, из бюджета ноды (не из доли
  пользователя) и отдаёт, когда кончается; полы одного пользователя — не больше четверти бюджета (одного
  соединения — всегда). Новое соединение, которое по пределам заменяет соединение того же пользователя
  (переподключившееся устройство, не слышное), берёт пол заменённого, как бы ни был занят бюджет. Иначе, если места
  нет, остальные соединения сначала отдают взятое сверх окна и полёта (как выше), и бюджет спрашивается ещё раз;
  всё равно нет — уступает и передаёт пол соединение того же пользователя по тем же правилам (свои учётные данные,
  самое тихое; иначе не слышное 35 с), даже если пользователь ниже своего предела соединений или пределы
  выключены: устройство, сменившее сеть, входит сразу, а не когда его старое соединение простоит 60 с;
  места всё равно нет или пользователь уже у своей четверти — новое соединение закрывается до ответа авторизации,
  как и отказанное пределом (клиент переподключается), это отказ вида `memory` при любом `conn_limit` (уступившее
  ради бюджета — тоже `memory`), а в журнал — два предупреждения по разу: бюджет ноды и четверть пользователя. Пол пользователя (до 16 × 1,75 МиБ ≈ 28 МиБ) больше не гарантирован: нода,
  чей бюджет занят, не берёт новых соединений ни у кого, кроме замен, пока другие не кончатся или не отдадут;
  зато память ноды честная. Без предела cgroup бюджет — восьмая `MemTotal`, рассчитанная на полы вне его, и
  полы остаются вне бюджета, как до v0.19.3 (до шага 4 raycontrol у юнитов нет `Memory*`).

С пределом cgroup это предел окон, полёта и полов: всё вместе — не больше бюджета (без предела — бюджета и полов,
16 × 1,75 МиБ ≈ 28 МиБ на пользователя). Вне бюджета остаётся:
- UDP: 256 сессий пользователя × (128 КиБ очереди + фрагменты двух пакетов, до 96 КиБ каждый), по тому, что сообщения
  держат, — до 80 МиБ, плюс буфер чтения сокета сессии (64 КиБ) и буферы ядра;
- неавторизованные: 768 КиБ окна на соединение, соединений — сколько пропустит фронт (до 1024 подтверждённых потоков
  с источника), и по 64 потока соединения до 10 с.

Куча под окном приёма бывает больше окна: кадр STREAM от 128 байт quic-go держит в буфере пакета (1452 байта), так что
у клиента, шлющего кадры по 128 байт, — до 11 раз больше окна, у заполняющего пакеты — около окна. Пока соединений
мало, окна почти прежние: на RTT 40 мс загрузка 1, 8 и 128 МиБ и выгрузка 1 и 128 МиБ одним соединением идут столько
же, сколько в v0.19.2, выгрузка 8 МиБ — 0,36–0,41 с вместо 0,35 с, пока окно растёт от 768 КиБ (по три прогона в
процессе через loopback, бюджет 2 ГиБ). Окна берут не больше половины доли (1/16 бюджета; окно quic-go растёт
удвоением), и на малом бюджете это предел одного соединения: на 32 МиБ (хост в 256 МиБ и меньше без предела cgroup,
юнит с пределом 85 МиБ) окно соединения останавливается на 1,5 МиБ, и выгрузка 128 МиБ на RTT 40 мс идёт 4,7 с
(около 27 МиБ/с, окно на RTT), 8 МиБ — 0,51–0,57 с; на хосте в 1 ГиБ без предела (бюджет 128 МиБ) окно доходит до
6 МиБ; в юните — до 6 МиБ при `L` = 256 МиБ, 12 МиБ при 512 МиБ и до 20 МиБ Hysteria с `L` около 822 МиБ.

### 3.3. dnsmux (UDP 53)

- Выбор бэкенда по суффиксу QNAME (без учёта регистра, по меткам): `<t>.example.com` → `dnstt`,
  `<v>.example.com` → `masterdns`. Остальное — `REFUSED`, открытым резолвером нода не становится.
- Отправитель запроса — рекурсивный резолвер, а не клиент: SPA к порту 53 не применяется. Аутентификация —
  ключ туннеля (Noise у dnstt, общий ключ у MasterDnsVPN).
- Оба туннеля не открывают соединений к произвольным адресам: каждый поток идёт в бэкенд `inner` (§3.9).
  Клиент поднимает VLESS с ML-KEM-768 к `inner` внутри туннеля.
- Копия запроса туннеля (её может прислать кто угодно на пути, с любого адреса) получает первый ответ или пустой,
  но никогда не новые данные (v0.19.3): у dnstt — память ответов в байтах и память ответивших запросов на срок метки
  dnsauth, у slipstream — ответ сервера по полю во фронте 5–10 с, не больше 4 ответов на поле
  ([`CONFIG.md`](CONFIG.md), `dns.zones[].tag` и бэкенд `dnstt`).
- Отрицательный ответ ниже вершины зоны с `ns` несёт SOA зоны (RFC 2308, v0.19.3).
- Ответы ограничены по блоку адреса назначения (/24, /48; v0.19.3): свои ответы фронта (`REFUSED`, вершина) — по
  темпу, ответы бэкендов — щедрым байтовым бюджетом, отрицательный ответ ниже вершины не задерживается, только теряет
  SOA сверх темпа ([`CONFIG.md`](CONFIG.md), «Пределы по адресу назначения»).

**dnstt** (апстрим v1.20260501.0, вендорен в `third_party/dnstt`, `replace` в `go.mod`; серверная часть — `dnsttserver/`):
1. Вынести серверную часть в библиотеку: `server.Run(ctx, Options{Domain, PrivKey, PacketConn, Upstream func() (net.Conn, error)})`.
2. `PacketConn` — виртуальный от IPC, `Upstream` — соединение с `inner` через unix-сокет.

**MasterDnsVPN** (`third_party/masterdnsvpn` форка `arngory/sing-box`, закреплён в `go.mod`):
1. Добавить серверу `SetPacketConnFactory` (для клиента такой патч уже есть: `SetListenerFactory`).
2. Режим `PROTOCOL_TYPE = "TCP"` с фиксированным upstream = `inner`. Режим `SOCKS5` на ноде не используется.
3. `DATA_ENCRYPTION_METHOD` = **5** (AES-256-GCM). Нода разрешает только AEAD (raycontrol R1-8): метод 2 у MasterDnsVPN — ChaCha20 без аутентификации. Ключ — файл с 32 символами через `LoadCredential=`; niko-server его только читает и никогда не генерирует.

**DNS-записи:**
```
*.example.com.   A   <IP>
<t>.example.com. NS  <ns>.example.com.
<v>.example.com. NS  <ns>.example.com.
```

### 3.4. Yggdrasil

Сделано в v0.4.0 (`nikoserver/yggdrasil.go`).

- **Подключение — только прямое (P-14).** Клиент указывает пир `tls://<адрес ноды>:443?sni=<y>.example.com&key=<ключ узла>`.
  tcpmux отдаёт поток по SNI бэкенду `yggdrasil` в режиме `fd`.
  - yggdrasil-go передаёт `sni` из URI в TLS: `tlsSNI` в `link_tls.go`.
  - Клиент Niko отправляет ClientHello Chrome через uTLS (`tls_fingerprint`).
- **TLS в бэкенде.** TLS 1.3, только `X25519MLKEM768`, сертификат имени `<y>` из `tls`. ALPN — `h2` и `http/1.1`,
  как у веб-сервера.
- **Проверка ключа.** Бэкенд читает рукопожатие линка (`meta`: TLV и подпись ed25519 над BLAKE2b ключа). Ключ должен
  быть в `users_file` (`yggdrasil.public_key`), подпись должна сходиться. Всё, что начинается не с `meta`, получает
  ответ сайта: пустой `404` по h2 или HTTP/1.1, смотря что выбрал TLS.
- **Перечитывание пользователей.** Файл перечитывается по `SIGHUP` и при изменении, без перезапуска. Линки удалённых
  ключей закрываются сразу.
- **Передача линка ядру.** Ядро yggdrasil-go (форк из `arngory/sing-box/third_party`) слушает unix-сокет в каталоге
  0700, который виден только процессу бэкенда.
  - Каждый линк приходит в ядро со своего адреса: ядро различает входящие линки по адресу собеседника.
  - Своего `AllowedPublicKeys` у ядра нет: проверку ключей ведёт бэкенд.
- **Выход.** На адресе узла в mesh работает стек gVisor. TCP на `exit_ports` уходит в `inner`, на другие порты —
  RST; UDP отбрасывается. Соединения выхода держат keepalive: клиент, пропавший из mesh, сброса не шлёт.
  - Выход берёт TCP только с адресов ключей из `users_file` (0x02…, /128), с остальных — RST; из подсетей ключей
    (своя /64 у каждого ключа в 300::/8) — тоже RST: Niko подключается с адреса, не из подсети. Адрес в mesh
    привязан к ключу (ipv6rwc), а с `peers` адрес узла виден всей сети: без этого выход открыл бы `inner` любому её
    узлу (ревью протоколов raycontrol, 2026-11-21). Адрес несёт около 112 бит ключа: ключ с чужим адресом не
    подобрать. Это защита в глубину: `inner` всё равно спрашивает, кто клиент.
  - Пользователь — имя записи в `users_file` до первого `-` (у raycontrol `u<id>`, `u<id>-<устройство>`, с `-n`
    и `-p` на время смены UUID); запись без имени — пользователь сама по себе. Выходов сразу не больше 4096 и не
    больше, чем их полов (96 КиБ) помещается в четверть памяти процесса `M` (§4): `N = min(4096, (M/4) / 96 КиБ)`,
    у одного пользователя — `N/8` с любых его ключей, от 64 до 512 (512 при 4096); рукопожатий, что ещё не закончились, у одного пользователя — не
    больше 64. Сверх любого предела — RST: стек берёт в работу до 5120 рукопожатий, больше, чем выходов, так что SYN
    без ответа не остаётся. Место выход занимает с SYN, до конца рукопожатия: SYN-ACK без ответа держал бы его две
    минуты, поэтому рукопожатия считаются отдельно. Каждый выход держит сокет к `inner` до того, как клиент скажет,
    кто он. Предел узла на пользователя ниже предела `inner` (conn-limit-v1, 1024 TCP на пользователя), так что через
    Yggdrasil первым срабатывает он, простым RST без причины. Все выходы займут не меньше 8 пользователей (при `N` от 512; меньше — меньше);
    простаивающий выход стоит около 53 КиБ.
  - Буферы выходов — в бюджете узла (с v0.19.2). Сам gVisor растит буфер отправки с окном перегрузки, а окно — и
    тогда, когда узкое место клиент, и буфер приёма — с тем, что читает узел, каждый до 4 МиБ. Выход, клиент
    которого не читает, держал до 4 МиБ, пользователь — около 2 ГиБ, узел — 16 ГиБ, с выгрузками вдвое больше.
    Теперь буферы выхода начинаются с пола (отправка 32 КиБ, приём 64 КиБ) и растут так, как растил бы их gVisor, до
    4 МиБ каждый: отправка, когда буфер полон, — до удвоенного окна перегрузки (вчетверо в медленном старте: иначе
    ответ в 1 МиБ шёл на RTT дольше); приём — до 1 МиБ с первого чтения, дальше по прочитанному за RTT. Каждый байт
    сверх пола берётся из бюджета узла, а пользователь берёт не больше восьмой его части (как 8 пользователей
    занимают все выходы). Бюджет — от памяти процесса (§4, «Память процесса»): с пределом cgroup ниже хоста — треть
    предела `L` (с v0.19.3; `memory.high` тоже), не больше 4 ГиБ; без предела — четверть `MemTotal`, от 64 МиБ до
    4 ГиБ; поля в конфиге нет. Это предел учёта gVisor: буферы всех выходов вместе учтены не больше чем на бюджет B и
    полы, B + N × 96 КиБ, где N — предел числа выходов выше: в юните не больше L/3 + L/4 = 7/12 L, у пользователя —
    B/8 + 512 × 96 КиБ (на хосте с 2 ГиБ без предела B = 512 МиБ и полы 384 МиБ; в юните с `MemoryMax` 1 ГиБ и
    `MemoryHigh` 896 МиБ — 298 МиБ и 2389 выходов, 224 МиБ полов).
    Буфер отправки считает байты данных, и куча под ним — около 1–1,2 его. Буфер приёма считает память сегментов
    по их длине, сверх него — один сегмент, а пакет лежит в куске пула степени двойки: куча под ним — до 2 его
    (1,4 при сегментах в 1280 байт, 2 при мелких; ревью протоколов). До v0.19.3 полы от памяти не зависели: на
    хосте с 512 МиБ это было 128 + 384 МиБ; теперь там 128 МиБ бюджета и 1365 выходов, 128 МиБ полов. Ещё около
    53 КиБ на каждый простаивающий выход. Тест: 80 выходов 10 пользователей,
    клиенты прочли по 2 МиБ и встали, бюджет 32 МиБ — куча выросла на 37–46 МиБ, без бюджета — на 250 МиБ.
  - Когда бюджета или доли не хватает, выходы отдают выросшее (если не хватает только доли — выходы того же
    пользователя; обход раз в 100 мс на пользователя и отдельно раз в 100 мс на узел): приём — если узел секунду
    ничего не читал от клиента и стек не держит ничего принятого, ни по порядку, ни за дырой; отправка — если узел
    секунду ничего не писал клиенту и неподтверждённое помещается в пол. Правый край окна приёма, уже
    объявленный клиенту, gVisor назад не двигает (`rcv.go:130-141`): после отдачи до 64 КиБ клиент может прислать
    до прежнего окна, лишнее стек отбрасывает с хвоста, и клиент шлёт его повторно. Сегменты за дырой стек держит до
    3/4 буфера, под которым они пришли, а под полом не впустил бы и сегмент самой дыры: по одной очереди по порядку
    клиент с дырой держал вне бюджета до 3 МиБ на выход, а дыра, заполненная позже, не заполнялась никогда.
    Сколько держит стек, gVisor наружу не отдаёт: узел читает его счётчик (`rcvMemUsed`) на версии из `go.mod`, тест
    это проверяет; без него приём не отдаётся. Выход, который ещё отправляет то, что `inner` уже закончил, своё
    держит. Доля пользователя — B/8 при любом числе пользователей, и между работающими выходами ничего не
    перераспределяется: 8 пользователей могут занять весь бюджет, остальные идут с полов (32 КиБ отправки —
    около 320 КБ/с на RTT 100 мс). Один пользователь — не больше своей доли. В журнал — по одному предупреждению
    на бюджет узла и на долю пользователя, без имён, а не на каждый выход. Пока выходов мало, окна прежние: на RTT
    40 мс загрузка и выгрузка 1, 8 и 128 МиБ идут столько же, сколько без бюджета, один выход доходит до 4 МиБ в обе
    стороны.
  - Соединения выходов, закрытые узлом первым, ждут в TIME-WAIT 1 с, а не 60 с, как по умолчанию в gVisor; таких
    и тех, что ждут FIN клиента в FIN-WAIT-2, вне всех пределов держится не больше 4096, сверх — самое старое
    получает RST. Раньше их не считал никто: 2705 после минуты коротких выходов подряд, около 11 КиБ каждое. SYN на
    четвёрку адресов в TIME-WAIT gVisor отдаёт только слушающему сокету, не форвардеру выходов, и клиент, снова
    выбравший тот же порт, ждал конца TIME-WAIT без ответа: 241 из 5000 коротких выходов подряд. RFC 9293 просит
    2 MSL (MUST-13), но то, от чего TIME-WAIT бережёт, здесь мало значит. Поздний FIN клиента, чей ACK потерян,
    получает RST в LAST-ACK, когда у клиента уже весь ответ и FIN узла. Старый сегмент, принятый в новое
    соединение, требует того же порта клиента и сегмента прежнего соединения, живого в mesh дольше секунды. ISN
    не случаен: это хеш четвёрки адресов плюс часы в 64 нс (gVisor и Linux, RFC 6528), так что нужно ещё, чтобы
    прежнее соединение пронесло больше 15,6 МБ за каждую секунду с его начала: тогда новое окно там, куда дошли
    его номера. PAWS у gVisor нет; у клиента с метками времени (Linux, macOS) есть, у Windows и клиентов на gVisor
    — нет. Испорченным оказался бы поток AEAD к `inner`: он рвётся, а не тихо портится.
  - FIN-WAIT-2 узла, закрывшего обе стороны, ждёт FIN клиента 10 с, а не 60: иначе выходы одного пользователя,
    кончаясь каждые 5 с, заняли бы все 4096 мест для ждущих. Это ожидание только закрытого соединения: пока узел
    закрыл лишь свою сторону, а клиент ещё шлёт, таймера нет, а полузакрытие клиента первым — это CLOSE-WAIT, и
    длинный ответ `inner` после него доходит целым. Данные клиента после закрытия обеих сторон получают RST.
  - Ключ, ушедший из `users_file`, теряет открытые выходы вместе с линками: сторона клиента получает RST, сокет к
    `inner` закрывается.
  - Когда `inner` закончил свою сторону, сторона клиента живёт ещё 5 с: молчащий клиент выход не держит.
    Полузакрытие клиента (FIN) уходит в `inner`, а сторону к клиенту `inner` заканчивает сам (у Xray это таймер
    бездействия, секунда по умолчанию): загрузка после FIN клиента не обрывается. Узел всё же держит свой предел:
    после FIN клиента сторона `inner`, если та молчит 2 мин, кончается RST клиенту — по FIN он счёл бы ответ
    целым.
  - Клиент, который 15 мин не берёт того, что его ждёт, выход теряет (RST), если ждёт больше, чем вмещает буфер
    отправки: у каждой записи к нему 15 мин, чтобы найти там место, а ждущая запись получает его, когда клиент
    подтвердит половину буфера (до 2 МиБ). Иначе подтверждённые пробы нулевого окна держали бы выход без срока.
    Медленный клиент не теряет: от 2,3 КиБ/с хватает (5 мин обрывали аудио на 32–48 кбит/с, пятое ревью). Не user
    timeout TCP: в gVisor он считает от первого повтора, пока не подтверждено всё отправленное, и обрывал загрузку,
    которая шла сквозь потери пути.
  - `inner`, закрывший сокет, когда часть байт клиента ещё не прочитана, даёт на unix-сокете ECONNRESET: его ответ
    целый, и клиент получает его весь, затем FIN. Так же, когда клиент ещё шлёт: запись к `inner` не проходит,
    но сторона `inner` дочитывается, а что клиент шлёт дальше, узел отбрасывает (с v0.19.2; раньше узел закрывал
    сокет и обрывал ответ, если `inner` успел записать всё и закрыться раньше, чем узел отдал ему байты клиента).
    Сторона `inner` тогда, как после FIN клиента, кончается, если молчит 2 мин: `inner`, закрывший только чтение и
    замолчавший, иначе держал бы выход вечно. Клиент, который шлёт и после ответа, через 5 с получает RST.
  - Место выхода держится, пока у узла есть что отправить клиенту, и после конца выхода — до 10 мин, потом RST.
    Раньше выход, закончившись, освобождал место, а стек ещё держал неотправленное: 800 таких соединений одного
    пользователя, 657 МиБ, вне всех пределов (четвёртое ревью).
- **Изоляция клиентов (v0.15.0, raycontrol `docs/spec/lan-v1.md` §2).** Ядро пересылало бы кадры ironwood между
  любыми двумя своими пирами. Бэкенд копирует линк не байтами, а по кадрам (`yggframe.go`), после `meta` в каждую
  сторону. В кадрах traffic, pathNotify, pathBroken и pathLookup он читает ключи источника и назначения, как их читает
  ironwood.
  - От клиента K проходит только источник K и назначение — ключ узла N; к клиенту — источник N и назначение K. У
    pathBroken роли меняются: он идёт обратно к источнику трафика. Любой конец может быть и ключом группы K
    (G(x) = G(K) ≠ ∅, с v0.16.0, ниже).
  - pathLookup (6) рассылается всем, кто может ответить (iw `bloomfilter.go:301-329`). От K проходит любой lookup
    его или его группы (источник K или в G(K)). К K — lookup его группы к кому угодно (за K, в его Wi-Fi, может
    стоять тот, кого ищут) и lookup узла (источник N) только того, на что K ответил бы сам: назначение K или ключ из
    его адреса (iw `pathfinder.go:62-64`), или ключ его группы. Иначе клиент, объявивший в bloom все ключи, получал бы
    lookup других клиентов к узлу и lookup узла к каждому из них — с полными ключами. Lookup группы к узлу (по ключу
    или адресу) к K не проходит (v0.16.0): он для узла, а узел пересылает lookup дальше, даже когда отвечает сам (iw
    `pathfinder.go:56-60`), с `from` отправителя — клиенту, объявившему в bloom узел.
- **LAN (v0.16.0, raycontrol `docs/spec/lan-v1.md`).** У ключа в `users_file` может быть группа
  (`yggdrasil.lan`, базовое имя пользователя `u<id>`). Ключи одной группы — устройства одного пользователя —
  достают друг до друга через узел по правилам выше; ключ без группы — только до узла, как в v0.15.0.
  - Группы читаются при каждом перечитывании файла; фильтр берёт их одним снимком на чтение линка, так что кадр
    судится по одному чтению файла, а новая группа видна со следующего чтения. Смена группы линк не рвёт, удаление
    ключа — рвёт, как раньше. Ключ узла ни в какой группе.
  - **Потолок пересылки** (§4.4 lan-v1): ведро токенов на группу, `lan_relay_mbps` Мбит/с (по умолчанию 20), запас —
    секунда, но не меньше самого большого кадра (131 070 байт), чтобы он проходил при любой скорости больше 0; при 0
    ведро пустое. Свободно только то, что клиент K и узел N шлют друг другу. Всё, что узел пересылает для группы,
    списывается один раз, по длине кадра (тип и тело); сверх потолка кадр отбрасывается (с ответом, как любой
    отброшенный кадр), TCP внутри сбавляет темп; при `0` через узел не проходит ничего (`yggRule.judge`).
    - **На выходе к клиенту K.** Кадр доходит до устройства через линк устройства, с какого бы линка он ни пришёл —
      другого клиента или публичного пира: там он и списывается. Это traffic, pathNotify, pathBroken от ключа группы
      K; lookup от ключа группы, каждая копия (узел шлёт lookup каждому, чей bloom заявляет его назначение); и
      собственный кадр узла не самому K. Такой кадр идёт устройству за K (`niko-ygg-via`, lan-v1 §2.3) или по пути,
      который узлу дал сосед: ответ на lookup — по его `from` (iw `pathfinder.go:66-70`), трафик узла — по пути из
      pathNotify (`pathfinder.go:198-210`). В оба пути сосед кладёт что хочет и направляет их на линк другого
      соседа. Lookup самого узла (его `from` — путь узла) свободен.
    - **На входе от K** — то, чего на выходе не списать: кадр к узлу от имени соседа (источник — ключ группы, «за
      K»). Узел отвечает соседу, и ответ на линке соседа — собственный кадр узла ему, свободный: эхо тех же байт,
      pathNotify по `from` lookup, трафик по пути из pathNotify. Ключи всех устройств пользователя — у него.
    - **С публичными пирами** (`peers`) кадр K соседу списывается и на входе: он может уйти через публичный пир, чей
      линк ядро набирает само, мимо фильтра. Тогда на выходе не списывается кадр от ключа, у которого здесь открыт
      свой линк, lookup тоже: его списали на входе, один раз, а не за каждую копию. Кадр K от имени соседа, у которого
      здесь своего линка нет (устройство за K), списывается и на входе, и на выходе: на выходе его не отличить от
      кадра с линка публичного пира. Это небольшой лишний счёт, только с `peers`.
    - Ревью v0.16.0 нашло, что прежнее списание на входе от клиента пропускало данные между двумя устройствами при
      любой скорости, и при 0 тоже: lookup к узлу (узел рассылает его дальше), ответ узла по `from` lookup, трафик
      узла по пути из pathNotify (и то и другое — и от имени соседа), эхо узла от имени соседа — и кадры с
      публичного пира. Тесты на маршрутизаторах ironwood (`TestNekoServerYggLANRoutes`) держат каждый путь, публичный
      пир — ещё и на настоящих ядрах.
  - Байты прошедших кадров — по группе в строке `traffic` сокета статистики (`up`, `down` = 0): пересылка идёт мимо
    `inner`, а так попадает в лимит трафика raycontrol (traffic-limit-v1 §2.2). Итоги — `relayed_frames`,
    `relayed_bytes`, `relay_dropped_frames` в снимке. В журнал — ни ключей, ни групп, ни кадров.
  - Замер (тест на настоящих ядрах, TCP 8 с, линк к узлу 12 мс в каждую сторону): при 20 Мбит/с TCP получает
    16,5–17,7 Мбит/с, а когда slow start перебирает запас и теряет окна вместе с повторами (2 прогона из 11), —
    около 3; при 8 — 4,1–7,2 или 1,0–1,7; без потолка — 27–51. Списание на входе давало на той же машине то же в
    пределах разброса. Поток пакетов в обход TCP: ровно запас и скорость (4 998 387–5 002 358 байт за 4,2 с при
    8 Мбит/с). Ведро с запасом 100 мс давало TCP 3–6 % — хуже.
  - Остальное молча отбрасывается, счётчик `dropped_frames` в `stats_socket`. В журнал о кадрах — ничего.
  - **Координаты — не длиннее 64 портов** (v0.16.0). `from` у lookup, путь и путь info у pathNotify — это
    координаты в дереве: путь от корня к узлу, порт на ступень (iw `pathfinder.go:37-41`, `67-76`,
    `router.go:637-670`), длиной в глубину узла. Без публичных пиров клиент не глубже 3; ironwood сам разбирает путь
    до 128 портов без выделения памяти (`wire.go:104-105`). На настоящем ironwood (`TestNekoServerYggPathDepth`) узел
    на глубине 12 под цепочкой маршрутизаторов: самый длинный путь на линке клиента — 13 портов, глубина клиента;
    на глубине 63 клиент (64) доходит, на 64 (65) — нет. Длиннее — данные клиента в пути: по `from` узел отвечает на
    lookup, по пути info шлёт свой трафик к ключу (`pathfinder.go:66-70`, `198-210`) — на порт публичного пира мимо
    всех счётчиков или обратно клиенту, раздувая свои же кадры к нему. Фильтр отбрасывает такой lookup или
    pathNotify в обе стороны (с ответом, счётчик `dropped_frames`); путь в 64 порта несёт до 512 байт.
  - **Кадры клиента к узлу узел берёт сам.** У traffic и pathNotify клиента с назначением N и у pathBroken с
    источником N (он идёт назад к N) фильтр переписывает водяной знак на месте нулём той же длины (n−1 байт `0x80`,
    затем `0x00`). `_lookup` узла не находит следующего шага, пока расстояние не меньше знака (iw
    `router.go:701-711`), и узел обрабатывает кадр сам (`router.go:603-616`, `pathfinder.go:95-103`, `238-247`) — как
    кадр с верным путём: знак не подписан и дальше не читается. Путём клиент ничего не направляет: ни трафик к
    порту другого клиента (отброс, ответ, знание, занят ли порт), ни ответ по выбранному им `from`. Кадры между
    ключами группы путь и знак сохраняют (ниже, известные утечки).
  - **За отброшенный кадр отвечает фильтр.** Пир ironwood, пославший кадр (кроме keepalive), рвёт линк, если за
    3 с ничего не пришло в ответ, а получивший кадр должен keepalive через 1 с, и любой его кадр этот долг гасит
    (iw `peers.go:127-181`). Без ответа отброшенный lookup убивал линк простаивающего клиента, а уход корня дерева
    (устаревшие пути узла ведут к другому клиенту) — линки и связь на секунды. Поэтому на линке, где кадр
    отброшен:
    - кадр клиента: клиенту — keepalive `01 01`, ответ, какой дал бы узел; узлу, если он ждёт ответа (долг мог
      погасить отброшенный кадр), — keepalive;
    - traffic к клиенту от узла или к узлу: ядру — pathBroken, какой послал бы ironwood клиента (iw
      `pathfinder.go:228-236`): путь — `from` трафика как есть, водяной знак `^uint64(0)`, источник и назначение
      трафика; он чинит устаревший путь узла. Клиенту, если он ждёт ответа, — keepalive;
    - остальное к клиенту: клиенту — «пинг», pathBroken от N к K с пустым путём и водяным знаком 0 (68 байт). Его
      ironwood никуда его не передаёт и отбрасывает (источник не его ключ), но должен за него keepalive узлу; этот
      долг гасит и любой другой его кадр. Узел ждёт ответа и после своего отброшенного кадра, как после прошедшего:
      если фильтр отбросит и этот кадр клиента, узлу — keepalive (с v0.16.0: устройство, вышедшее из группы,
      продолжало слать прежним соседям трафик, тот отбрасывался, и линк рвался через 3 с). Иначе ядру за клиента не
      отвечают: линк, чей клиент пропал молча (TCP без сброса), остаётся без ответа, и ядро рвёт его за 3 с, сколько
      бы клиента ни искали.
    - Тот, кто перебирает порты, ничего о них не узнаёт: его кадры к узлу узел берёт сам, отброса нет.
    - Один ответ на кадр и только на этом линке; ожидают не больше одного keepalive и одного пинга на сторону.
      Запись — целыми кадрами под одним замком на сторону; ожидающие кадры — не больше 16 КиБ на сторону, пишет их
      своя горутина, отбрасывающий не ждёт.
  - **Packet Too Big — только своему.** ipv6rwc ядра отвечал на пакет больше MTU сообщением ICMPv6 Packet Too Big
    с 512 байтами пакета на адрес источника, ещё не сверив его с ключом отправителя: клиент, подставивший адрес
    другого, слал ему свои байты через узел. В форке (`5afe92f`) адрес сверяется раньше.
  - Кадр, который ядро не приняло бы (длина больше 131070 байт, пустой, разбор не сходится), закрывает линк.
  - Остальные типы (keepalive, дерево, bloom) проходят как есть.
  - Ядро не отвечает на удалённые getSelf, getPeers, getTree (`DebugPrivacy` форка): иначе getPeers отдавал бы ключи
    всех подключённых устройств.
  - **Известные утечки, оставлены сознательно** (переписывать bloom и дерево — риск для маршрутизации):
    - bloom узла к клиенту содержит ключи (их /64) всех остальных пиров на дереве (iw `bloomfilter.go:216-234`,
      ygg `src/core/core.go:96-98`): клиент проверит, на узле ли адрес, который он уже знает, но не перечислит.
      Ключи устройств выводит сервер, чужим они неизвестны;
    - дерево: пир получает анонсы цепочки предков узла и своей (iw `router.go:332-389`). Корень — наименьший ключ;
      без публичных пиров это обычно клиент, и его ключ получают все клиенты. Это один случайный ключ без имени,
      трафик к нему всё равно отбрасывается;
    - bloom как канал между двумя *сговорившимися* клиентами: биты, что A ставит в свой bloom, узел сливает в bloom
      для B (iw `bloomfilter.go:216-234`) — до 8192 бит на обновление. Через узел у них и так есть интернет:
      нового это им не даёт;
    - память: пока большой кадр приходит по частям, линк держит буфер самого большого кадра (131 080 байт) на
      сторону;
    - между ключами группы кадры сохраняют путь и водяной знак — по ним узел их и пересылает. Устройство в группе
      может направить кадр на любой порт узла и по тому, что вернётся (pathBroken узла или ничего), узнать, сидит ли
      на порту клиент: сколько их и на каких портах, но не чьи. Для кадров к узлу v0.15.0 это закрыл нулевым
      водяным знаком; между соседями ноль оставил бы узел без пути (v0.16.0);
    - **публичные пиры** — мимо и `lan_relay_mbps`, и лимита трафика raycontrol, в обе стороны (lan-v1 §7.4: линкам,
      которые ядро набирает само, нужен свой хук; закрыть — только фильтром и на них):
      - внутрь: источник кадра с их линка — какой написал отправитель. От имени узла или ключа, у которого здесь
        свой линк, кадр проходит к клиенту без списания. Ключ своего устройства у пользователя есть, так что от имени
        такого ключа идут и настоящие шифрованные сессии. В тесте (`TestNekoServerYggLANPublicPeers`) — около 76 МБ
        за 2,5 с при `lan_relay_mbps` 0, от имени самого устройства с публичной стороны — ничего;
      - наружу: свой lookup клиента к узлу и свой pathNotify узлу бесплатны, как всегда. Направив `from` или путь
        info на порт публичного пира, клиент шлёт туда свои данные ответом узла или его трафиком к себе. Так может и
        клиент без группы: это пришло с публичными пирами, а не с LAN. Ревью нашло 151 МБ и 69 МБ за 3 с при путях в
        8000 портов; с потолком в 64 порта (выше) такой кадр отбрасывается, а с путём в 64 порта в тесте за 2,5 с
        наружу ушло около 1 МБ ответов на lookup по кадру в миллисекунду и около 20 МБ трафика узла, который повторяет
        последний путь info в каждом кадре. Каждый кадр — не больше 64 портов, то есть 512 байт данных, но частоту
        кадров ограничивает только сам клиент.
- **Публичные пиры.** Включаются списком `peers`; по умолчанию его нет. С ними изменённый клиент обходит
  `lan_relay_mbps` и лимит трафика raycontrol в обе стороны (выше, известные утечки).
- **Постквант.** См. [`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md),
  вопрос 5.
  - Линк — TLS с `X25519MLKEM768`, при прямом подключении он и есть весь путь.
  - Сквозное шифрование Yggdrasil классическое, поэтому полезный трафик идёт в `inner` (VLESS с ML-KEM-768).

### 3.5. SPA

SPA v2 — [`spa-v2.md`](https://github.com/arngory/raycontrol/blob/main/docs/spec/spa-v2.md):
ключи устройств по эпохам, порт по слотам, scope и время внутри пакета XChaCha20-Poly1305. Пакеты принимает
`rayspa` через NFLOG и добавляет адрес в allow-наборы портов из scope. niko-server в SPA не участвует.

Клиент Niko отправляет SPA v2 (`libcore/knock/spa2.go`, векторы raycontrol проверяются побайтно), по UDP, а при неудаче — TCP-носителем (`spa-v2.md` §10, с v1.12.1).
Niko SPA v1 (`libcore/knock/spa.go`, шаг `ПОРТ/spa:КЛЮЧ`) остаётся в клиенте только для сторонних серверов.

### 3.6. REALITY в Xray

```json
{"inbounds":[{"listen":"/run/niko/xray-reality/reality.sock,0660","protocol":"vless",
  "settings":{"clients":[{"id":"<uuid>","flow":"xtls-rprx-vision"}],"decryption":"none"},
  "streamSettings":{"network":"raw","security":"reality",
    "sockopt":{"acceptProxyProtocol":true},
    "realitySettings":{"target":"/run/niko/site/tls.sock","xver":0,"serverNames":["<r>.example.com"],
      "privateKey":"<xray x25519>","shortIds":["<8 hex>"],
      "mldsa65Seed":"<xray mldsa65: Seed>"}}}],
 "outbounds":[{"protocol":"freedom"}]}
```

- **`mldsa65Seed` обязателен.** Клиент проверяет подпись по ключу из профиля (`pqv=` в ссылке); совместимость
  проверяет `xray-interop.yml`.
- Ключи REALITY, shortId и SNI ротирует raycontrol (пользователи — через gRPC API Xray без перезапуска).
- **`minClientVer`** не задавать (по умолчанию 26.3.27) или ровно `"26.3.27"`: Niko сообщает эту версию.
- **Постквант:** гибридный ключ X25519MLKEM768 (обязателен в Xray с 26.9.8). Клиент — отпечаток `chrome`.

### 3.7. NaiveProxy

- Бэкенд `naive` (inbound из форка, h2 и QUIC), сертификат `<n>.example.com`.
- Запросы без авторизации и не CONNECT получают сайт, без `407`.
- **Постквант:** `CurvePreferences = [X25519MLKEM768]` без отката. Клиент naive (Chromium) предлагает его по умолчанию.
- В клиенте Niko naive работает через плагин (форк `arngory/naiveproxy`); совместимость — в CI.

### 3.8. DoH

- Бэкенд `doh`: `https://<n>.example.com/dns-query/<token>` (h2 и HTTP/3), резолвер — DNS-роутер sing-box.
- **Постквант:** только `X25519MLKEM768`.
- DoT/DoQ (853) не поддерживаются.

### 3.9. Внутренняя ступень `inner`

- VLESS-сервер с `decryption` ML-KEM-768 (`mlkem768x25519plus`), пользователи — от raycontrol.
- Принимает потоки от `dnstt`, `masterdns`, `yggdrasil`, olcRTC и OpenFlux (unix-сокет), выпускает в интернет.
- Серверной части VLESS encryption в форке sing-box нет, поэтому `inner` работает на Xray, пока сервер не перенесён
  в форк (см. [`RAYCONTROL.md`](https://github.com/arngory/niko/blob/claude/intelligent-allen-0oa8na/docs/server/RAYCONTROL.md), вопрос 1). Клиент Niko против Xray с `decryption` уже проверяется в CI.

### 3.10. olcRTC и OpenFlux

- Форки: `arngory/olcrtc` (движок Ghostlane), `arngory/OpenFlux`. На ноде — отдельные процессы под управлением
  raycontrol, входящих портов нет.
- Режим фиксированного upstream: каждый поток идёт в `inner`, произвольных соединений сервер не открывает.
- OpenFlux: шифрование обязательно, выход L4, без root.
- Аккаунты платформ: режим `node` (выделенные аккаунты на ноде) или `client` (пользователь входит в клиенте).

## 4. Конфиги и команды

- Конфиги фронта, бэкендов и Xray генерирует raycontrol по схеме из [`CONFIG.md`](CONFIG.md) (версия схемы — поле
  `schema` в каждом конфиге). Источник правды — база raycontrol.
- Секреты (ключи, пароли, сертификаты) — пути к файлам из `LoadCredential=`, не строки в конфиге.
- `SIGHUP`: перечитать пользователей и ключи без разрыва соединений; соединения снятых пользователей закрываются
  (Yggdrasil, с v0.15.0 Hysteria2). С v0.17.0 бэкенды Hysteria2 перечитывают так же файл-выключатель пределов
  соединений (`conn_limit_file`). Смена портов и доменов — перезапуск.

Команды niko-server:
- `niko-server front -c <файл>`, `niko-server backend -c <файл>`;
- `niko-server check -c <файл>` — проверка без запуска; ненулевой код и понятная ошибка. raycontrol вызывает её
  перед каждым применением.

`init`, `export` и подписка — в raycontrol (`rayctl`), формат ссылок задаёт raycontrol (решение P-10).

Деплой (ставит raycontrol): systemd-юнит на каждый процесс, отдельные пользователи, фиксированные UID, секреты через
systemd credentials (TPM при наличии), systemd-resolved stub выключен (UDP 53).

**Память процесса (v0.19.3; raycontrol `docs/spec/memory-v1.md`).** Пределы задаёт юнит (`MemoryMax`, `MemoryHigh`
долями памяти хоста); процесс читает их при старте (`nikoserver/memlimit`): наименьшие `memory.max` и `memory.high`
своей cgroup и её предков (v2: путь из строки `0::` `/proc/self/cgroup` под точкой монтирования cgroup2 из
`/proc/self/mountinfo` (из нескольких — та, чей корень — самый длинный префикс пути; корни с `..` — вне
пространства имён, мимо), за вычетом смонтированной там cgroup, без неё — под `/sys/fs/cgroup`, а не найденный путь —
от корня монтирования; v1: `memory.limit_in_bytes` иерархии с контроллером `memory`, и общей, `cpu,memory`), и
`MemTotal`. `max`, мусор, 0 и значение выше `MemTotal` — не предел; равное — предел (lxcfs, `MemoryMax=100%`). `L` —
меньшее из двух пределов; `M` — `L`, без предела `MemTotal`. Из них:
- предел Go: если `GOMEMLIMIT` не задан и `L` есть, фронт и каждый бэкенд ставят `debug.SetMemoryLimit` в
  `min(high, max × 15/16) × 7/8` (бэкенд) или `× 3/4` (фронт: очереди его сокетов — unix к бэкендам нигде не
  учитываются, TCP и UDP идут в memcg — Go не видит), не меньше 64 МиБ; одна строка в журнале на `info`, только
  цифры. Без предела cgroup ничего не меняется: предел от всей памяти хоста ничего не даёт. Go 1.27 сам читает
  только `cpu.max`;
- бюджет Hysteria2 — `min(3L/8, 2 ГиБ)`, полы соединений внутри, у пользователя — не больше четверти (§3.2); без
  предела `MemTotal/8` от 32 МиБ до 2 ГиБ, полы вне его, как прежде;
- бюджет выходов Yggdrasil — `min(L/3, 4 ГиБ)`, без предела `MemTotal/4` от 64 МиБ до 4 ГиБ; выходов —
  `N = min(4096, (M/4) / 96 КиБ)`, у пользователя `N/8` от 64 до 512 (§3.4).

Цифры — в [`CONFIG.md`](CONFIG.md), «Память процесса». `niko-loadgen -cgroup` запускает бэкенд с этим пределом с
самого старта: под systemd — в его scope (`systemd-run --scope -p MemoryMax=… -p MemorySwapMax=0`), иначе в своей
cgroup (v2, а без контроллера памяти в v2 — v1; не под корнем пространства имён cgroup); нужен root. Печатает
`oom_kill` перед остановкой, а у scope — ещё `Result` юнита (`oom-kill`, если ядро его убило: cgroup убитого scope
к тому времени уже нет), после чего `systemctl reset-failed`; свою cgroup убирает и при ошибке, и по SIGINT и
SIGTERM.

## 6. Проверки (критерии готовности)

Каждый пункт — job в CI (GitHub Actions).

1. **Клиент Niko ↔ нода** для каждого протокола после SPA v2: REALITY с ML-DSA-65, Hysteria2 masq и obfs, naive h2
   и QUIC, DoH, dnstt и MasterDnsVPN с `inner`, Yggdrasil через `<y>`. Ожидается `204` от `generate_204`.
2. **Периметр:** без SPA все порты, кроме UDP 53 и порта слота, молчат (drop); повтор и пакет старше 30 с не дают доступа.
3. **Зондирование после SPA:** чужой SNI получает приманку; naive без авторизации — сайт; UDP-мусор на 443 — без ответа;
   DNS-запрос к чужому имени — `REFUSED`.
4. **Постквант:** клиент без `X25519MLKEM768` не подключается к hy2-obfs; у hy2-masq (с v0.19.3), naive и DoH
   (raycontrol v0.36.1) проходит рукопожатие, как у сайта, и получает ответ сайта или маскировку, а не туннель.
5. **Совместимость:** официальный клиент hysteria (salamander), Xray-клиент (REALITY), naive (форк), dnstt-client.
6. **Нагрузка:** 200 одновременных потоков через каждый мультиплексор, с разделёнными процессами. Без утечек
   горутин и роста памяти за 10 минут. Если копия UDP через фронт — узкое место: `SO_REUSEPORT` + eBPF.

## 8. Что доделать в клиенте

- ~~Импорт `rcdev1:`~~ — сделано в v1.11.0: вставка из буфера (буфер после импорта очищается) и QR. Нода хранится
  в настройках, `device_key` — обёрнутым ключом Android Keystore (AES-256-GCM, неэкспортируемый), в бэкап не
  попадает. В ядро ключ передаётся по ссылке (`spa_v2.device_key_ref`), в JSON конфига его нет. Профили с адресом
  ноды автоматически получают SPA v2 со scope «все разрешённые». Ноды видны и удаляются в «Настройки → Ноды raycontrol».
- ~~Предупреждение о неверных часах~~ — сделано в v1.13.0 по полю `time` подписки; при молчании ноды — подсказка проверить время (v1.13.1).
- ~~Подписка с ротацией~~ — сделано в v1.13.0–v1.13.2: «текущие + следующие», автообновление к `next.from` и до `expires`.
- Ротация UDP-портов сервисов — ждёт `services[].port_key` от raycontrol.
- Вторая ступень: исходящий VLESS с ML-KEM-768 к `inner` через detour (dnstt, MasterDnsVPN, olcRTC, OpenFlux).
- Пир Yggdrasil с `?sni=` (§3.4).
- Для нод raycontrol — только TLS с `X25519MLKEM768`, без отката.
